# Art

The art pipeline, the world art and the spell and equipment art. Moved word for word from `CLAUDE.md`, one `##` section per sprint. Sections name each other (for example "see Obstacles"); find them in this folder (the index is in `CLAUDE.md`, "Where the detail lives").

## Art pipeline (Sprint 13a)

- **Sources and outputs.** `art/palette.txt` has `color <letter> <hex>` lines (fixed colours) and `variant <id> <5 hex>` lines (the five ramp slots `1` to `5` of an element: body dark, mid, light, trim dark, trim light). `art/sprites/<name>.sprite` has `size w h`, `anim name first last fps loop|once`, then `frame` blocks of letter rows (`.` is clear). A sprite that uses ramp slots is built once per variant (`none`, `fire`, `thunder`, `land`, `sea`), others once as `base`, and a sprite whose source has an `outline` header line (the 21 enemy sprites: an elite's outline is the only thing that shows a silhouette) also gets a white `_silhouette` sheet, while every other sprite gets none (spring cleaning; `SpriteSource.outline`, ignored on a tile or sliced sprite, and `SpriteLibrary.find_silhouette` is null for one without). `godot --headless -s tools/art/art_builder.gd` writes `assets/sprites/<name>_<variant>.png` (frames side by side) and a `SpriteSetData` `.tres` beside each; run `godot --headless --import` afterwards. Outputs are committed, so the game never needs the tool.
- **Code.** `ArtPalette` and `SpriteSource` parse, `ArtBuilder` builds, `SpriteLibrary.find(name, variant)` looks a set up (falling back to `base`), `SpriteSetData.frames()` builds and caches a `SpriteFrames`. Frame rates and loop flags live in the `.sprite` header, never in code.
- **`BodyView`** (a Node2D that builds its own `Outline`, `Sprite` and `Fallback` children) replaced the `Body` rectangle of the player, `Enemy` and `Boss`: `set_look`, `play`, `set_facing`, `set_tint`, `set_outline`, `counter_scale`, `fallback_color`. With no art it shows the old coloured square (`fallback_color`), so a missing sprite never crashes or hides an entity. The hit flash sets `modulate` and a tint sets the sprite's `self_modulate`, so they multiply and never fight.
- **1:1 rule.** The sprite is never scaled: `counter_scale(scale)` undoes the owner's scale (which sizes the 12 px hit shapes), so a Tank or the boss is a bigger drawing, not a stretched one. The sprite never decides collision.
- **Naming.** Enemies are `enemy_<archetype id>` in the element's variant (`EnemyData.element_id`, set by `EnemyComposer`), the boss is `boss_<boss id>`, the player is `player`. State animations: `move`, `death`, and one of `attack` (Ranged, 12 fps, once), `fuse` (Exploder, loop) or `pulse` (Support, once) per enemy, started through `Enemy.show_state(state, seconds)`. Boss: `idle`, `telegraph`, `attack`, `vulnerable`. A death animation frees the enemy once (with a 1 s safety timer).
- **Tests.** `tests/test_art_assets.gd` rebuilds every sprite in memory and fails if a committed PNG or `.tres` differs (pixels, and animation names, ranges, fps and loop), if a pixel is not a palette colour, if a frame touches its 1 px margin, if a set does not load, or if an output file belongs to no source or variant (an orphan would still be loaded, since `SpriteLibrary` tries the element's variant before `base`; delete it). Edit a `.sprite` and forget to run the tool, and it fails.
- **Replace art** by editing the grid and re-running the tool, or by drawing the sheet: overwrite its PNGs (same frame size and frame order) and add a `hand_drawn` line to the `.sprite` (`SpriteSource.hand_drawn`). The tool then never rebuilds that sprite's sheets, still writes its `.tres` from the header and makes its silhouette from the first sheet (`ArtBuilder.silhouette_of`) when it declares an `outline`, reports a missing sheet, and the asset test checks only the sheet size and the silhouette. Without the line the next tool run overwrites a drawn PNG and the pixel test fails. Checked in a real window: a recoloured sheet shows with no code change.
- **Performance.** Drawing 300 sprites costs about 30% of the stress frame rate against rectangles (about 139 against 199 fps with `--obstacles --drops`). Animation itself costs nothing measurable. A runtime shared texture atlas is the next lever if a slow device struggles. `BodyView._process` runs only while an outline is shown.

## World art (Sprint 13b)

- **The map names its art.** `MapObstacle.material` (`stone`, `hedge`, `tree` ...), `MapMaze.material` (stamped on every wall it generates), `MapZone.floor_style`, `MapData.floor_style` and `border_style`. `WorldArt` (static) resolves a name by one rule through `SpriteLibrary`: `tile_<style>`, `wall_<material>`, `post_<material>` (base variant). **A name with no art is null and the caller keeps today's flat colour**, so a missing sprite never hides a wall or breaks a map. Nothing branches on a map, zone or material id.
- **Two new `.sprite` markers.** `tile` (full-bleed repeating tile: no transparent pixel, no 1 px margin rule, no silhouette) and `slice <left> <top> <right> <bottom>` (a tile's 9-slice margins in pixels, for walls), both carried into the `SpriteSetData` (`tile`, `slice`). The palette limit is 64 colours (was 40) with a world section.
- **Floors.** `GameMap` keeps its `Border`, `Floor` and `Zone_*` `ColorRect`s (the flat fallback colours) and adds `BaseArt` (the border and map `FloorPatch`es, hard-edged, before `Zones`) and `ZoneArt` (one soft `FloorPatch` per zone with a floor style, after `Zones`). A zone with floor art hides its flat tint (the node and its colour stay), because the soft edge must show the floor below, not a straight-edged rectangle. `FloorPatch` draws a tiled rectangle for its middle and, for a soft one, the outer 32 px in 8 px cells with how deep the gap reaches following smooth noise along the edge (wavy bays, never a straight line; the first version, a 16 px band with random cells, still read as a straight line). **The middle ends on the 8 px cell grid** (`interior_rect()`), because cutting it at "size minus 32" left a bare strip, where the grass showed, through every zone whose size is not a multiple of 8 (found in the review; `test_every_pixel_is_covered_once_for_any_size` pins it). **A stone zone is sized to its structure grown by at least 48 px**, so its wavy edge lies outside the walls and the floor inside is solid (the first map's maze zones are 832 by 592, the island 520 by 384, the tunnel 680 by 200).
- **Walls and posts.** `DrawChunk` draws a RECT obstacle as a 9-slice (`NineSlice`: corners 1:1, edges and centre tiled 1:1, never stretched) of its `wall_<material>` tile and a CIRCLE as its `post_<material>` sprite (one size, about 44 px, so a post can differ from its collision radius by up to about 4 px; collision stays authoritative). Corners and edges of every wall are drawn first and the centres second, **as two passes over the whole layer** (`ObstacleLayer`: the border chunks, then a `Centres` node of centres-only chunks after them; `chunks()` lists the border ones), so where walls cross there is no border line across the junction even when the two walls are in different 512 px chunks (a per-chunk second pass left 11 seams on the first map). An obstacle with no art keeps the grey fill. The layers stay chunked, so off-screen chunks cost nothing.
- **Lectern, points of interest and pickups.** Each has a `Body` (`BodyView`) with the old shape kept as the fallback: the Lectern's `idle` glow, a point's `ready` and `used` (dimmed while refreshing; a merchant is never refreshing) from `PointOfInterestData.sprite_name`, scrolls by category (`scroll_base`, `scroll_area`, `scroll_buff`, white so the scroll's colour tints them, `sparkle` for Rare) and `pickup_xp` (blue, so it stands out on grass and stone) and `pickup_gold`. **A kill's drops never hide each other (user feedback):** pickups draw by value through `z_index` (a scroll 2, an XP gem 1, a coin 0), and `ValueDropper.drop_offset` (set in `main.tscn`: XP (-7, 3), Gold (7, 3), applied only in `on_enemy_died`, never in `place`) fans XP to the left and Gold to the right of where the scroll lands. The bob shader moves onto the sprite through `BodyView.set_sprite_material`. With art, a point draws only its ring and the old rectangles are drawn only when there is no sprite.
- **Shadows (user request): things that move, can be picked up or can be used have a soft oval shadow; static things (walls, trees) have none, so a player can tell them apart.** `BodyView.shadow_enabled` (set in the scenes of the player, enemies, boss, Lectern, points of interest and the three pickups) adds a `Shadow` sprite behind the sprite: the biggest of `shadow_8/12/16/24/32` no wider than the sprite, at its feet in world pixels (kept 1:1 under a scaled owner), 40% see-through, none without art. **Every shadow is drawn at one absolute depth, `BodyView.SHADOW_Z` (-1), and `GameMap` draws its floor layers (Border, Floor, BaseArt, Zones, ZoneArt) one below it**, so the shadows come together in the draw order and batch: a shadow between every pair of sprites cost about half the frame rate at 300 enemies (about 140 down to about 77 fps), and the shared depth brings it to about 115. Walls and trees stay at depth 0, above the shadows.
- **The first map's look.** Grass plaza (**every sprite stays at the game's one pixel size, never scaled**, a user rule); the mazes, the stronghold and the tunnel all share the one lavender `ruin` floor and the one `stone` wall (user decision after seeing several textures at once); every post is a tree; the plaza's small walls are `hedge`. (The unused brick wall, `path` and `hall` floors, marble post, grass and moss decorations and scroll icon were deleted in the spring cleaning.)
- **Performance.** Few textures with many uses: stress with `--obstacles --drops` at 300 enemies is the same as main within noise (about 141 against about 135 fps median), so no baking was needed.
- **Art taste (user feedback during the build):** brighter, simpler and more cartoon; fewer textures at once; walls players recognise (stone or brick, not gem-like hedges); trees, not pillars; transitions that look natural.

## Spell and equipment art (Sprint 13c)

- **An element's look is data.** `ElementLook` (`resources/spells/element_looks/{fire,thunder,land,sea}.tres`) holds the hit-area `tint` and `edge`, the `effect_sprite`, the `orb_sprite` prefix and `rises` (Fire and Land rise from the ground, Thunder and Sea fall from the sky). `ElementLooks.for_element(element)` finds it (null for no element, which keeps the flat look) and `ElementLooks.id_of(element)` names an element for sprite variants (`fire`, `thunder`, `land`, `sea`, `none`).
- **Area spells (Cone, Line, Zone).** The exact polygon and hitbox never change. `SpellSkin.dress` tints the polygon and adds a 1 px `Edge` `Line2D`, then spawns effect sprites: `EffectPlan` (pure) gives `count_for(area)` (one per 600 px², 3 to 24), `spots` (best-candidate spread inside the polygon, seeded) and `delays` (rising effects nearest the caster first, falling ones in a random order, over the first 40% of `SpellSkin.INSTANT_LIFE`, 0.35 s; a Zone uses its tick interval). A hybrid spell cycles through its elements sprite by sprite. `SpellSkin.pulse` spawns a fresh set at each Zone damage tick, and `SpellSkin.tint` only tints (the Wave).
- **`EffectSprite`** is a top-level `AnimatedSprite2D` (`play` once, then a fade, then freed) placed in world pixels with its base on the spot, a child of the area's PARENT because an instant area frees in 0.12 s while its sprites play about 0.45 s, and because a rotated or scaled area must not rotate or scale a sprite (one pixel size). At most `MAX_LIVE` (160) live; sets are cached by folder and name (the library's resource cache drops an unheld set, so every spawn built its own frames).
- **Missiles and Waves.** A Missile with an element look shows `Orb` (a `BodyView` on `<orb_sprite>_12|16|24`, class from `MissileArea.orb_class(size)`: up to 1.2 is 12, up to 2.0 is 16, otherwise 24), the node is NOT scaled and only the hitbox is (`_hitbox.scale`), so the hit follows `effective_size()` exactly and no pixel scales; with no art the old square scales with the node as before. The orbs are upright and have no directional trail (they are never rotated). A Wave carries a row of orbs (`WaveArea.orbs()`, one per about 10 px, 2 to 24, top-level, re-spaced every step as it widens).
- **Enemy attacks.** `EnemyProjectile.fire(..., element_id = &"")` (a default, so old calls work): the shot is `fx_enemy_orb` (a ramp sprite, so the element variants colour it) with a dark outline so it stands out from the player's spells; `BrainKeepDistance` passes `enemy.data.element_id`, the boss `ElementLooks.id_of(data.element)`. `BlastZone` warns with rings of `WarningMark` sprites (an outer ring on the circle, a bright inner ring that grows with the fuse and flashes, about one mark per 10 px, at least 8) and ends in `fx_blast_burst` (several for a big zone); without art it draws its old circles. The boss's Charge warning is a dashed line of `WarningMark`s (`Boss.charge_marks()`, top-level because the boss is scaled x3). `TargetReticle` shows `reticle`, with the old ring as the fallback.
- **The wizard is drawn in layers.** `BodyView.add_layer`, `set_layer(layer, sprite, variant)`, `clear_layer`, `layer_names()`: each layer is an `AnimatedSprite2D` above the body that copies its animation, frame and flip every frame (processing is on only while a layer or outline is shown, and layers are counter-scaled like the sprite). `PlayerLook.apply(body, profile, catalog)` sets `robe`, `beard`, `headwear` and `weapon` (the same ownership and slot rules as `ShopSystem.bonuses`); an empty robe or headwear slot shows the starter (`robe_starter`, `hat_starter`), the weapon slot shows nothing and the white beard (`beard_white`) is always worn. `Player._ready` applies it with no profile (the starters) and `RunStart.prepare` applies the profile, so equipping in the shop takes effect at the next run.
- **No skin shows (user request).** The bare wizard (`player_body`) has a face in the hat's shadow with only two eyes, the beard covers the rest, and the hat (a 12 px band and a 14 px brim) and hood are wider than the head; a test fails if any wizard layer or equipment sprite contains a skin colour. `art/sprites/player.sprite` is the composite of the four layers (body, robe, beard, hat) kept as the fallback and as the reference of `test_the_starter_layers_compose_to_exactly_the_wizard`; regenerate the four layers and the composite together.
- **Equipment is data.** `EquipmentData.sprite_name` and `sprite_variant` (a palette variant): `robe_wizard` (fire, land, thunder, sea, none for Ember, Stone, Storm, Tide, Warded), `hat_pointed` and `hood_soft` (hardy, mana, swift), `wand_short` (flicker, quick), `staff_tall` (oak, elder). The equipment sprites are 16x16 with the wizard's eight frames and animations and follow the walk bounce (rows lift one in frames 3 and 5) and the cast; `hat_pointed` is the starter hat's exact shape.
- **Pipeline.** `variants <id> ..` in a `.sprite` limits which colourways a ramp sprite is built in; without it a ramp sprite is built in the five element variants only (`ArtPalette.ELEMENT_VARIANTS`). The item variants reuse colours the palette already has (it sits at 63 of 64).
- **Performance.** Effect sprites cost about 13 to 16% of the frame rate against main in the full stress scene and a Zone (a Line and a Wave are equal), well above the 60 fps target.
