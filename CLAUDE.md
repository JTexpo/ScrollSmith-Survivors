## Architecture (big picture)

The core idea is that spells are **assembled at runtime from data**, never hardcoded per combination. A spell is a **Base** (one or more elements: Fire/Thunder/Land/Sea), exactly one **Area** (Line/Cone/Area/Missile), and optional **Buffs**.

Layering, per `technical-design.md`:

- **Scenes** are physical objects and UI (Player, Enemy, Projectile, Lectern, HUD, crafting menu).
- **Scripts** hold logic and systems.
- **Custom `Resource`s** hold all data definitions: `SpellData`, scroll, `EnemyData`, equipment and potion definitions.
- **Autoloads** are only for truly global or persistent state (Game/Run/Save managers). Avoid adding more.

Systems that must stay separate and reusable:

- **Spell Definition vs. Spell Instance.** `SpellData` is static configuration. A spell instance is the equipped runtime object with its own mana pool. Two instances of the same definition must never share mana.
- **Spell Builder.** It computes final damage, max mana, mana cost, cast interval, area dimensions, and buff effects. It must be independent of the crafting UI and the Lectern scene.
- **Crafting System.** It validates a combination, consumes scrolls, and creates or equips the spell. Invalid combinations must not consume scrolls. The Lectern is only the interaction point.
- **Damage System.** Elemental math is centralized in one place. Spells and enemies must not compute their own. Multipliers are configurable, not hardcoded. Several Base types combine by **best match**: a hit uses whichever of the spell's elements does best against the enemy (strong beats neutral beats weak, the first wins a tie), computed only in `DamageSystem.resolve`.
- **Area behaviors.** Each Area is an interchangeable implementation behind one casting interface. Modifiers like Duplicate Area must not require editing individual Areas.
- **Progression.** Run progression (XP, levels, slot unlocks) is separate from permanent progression (Gold, equipment, saves).
- **Equipment.** Effects go through one central modifier system, not direct edits to player stats. Hats and Hoods differ only visually.
- **Player, UI, and inventory.** The Player delegates to systems and holds no spell, enemy, or crafting logic. UI reads from systems and never mutates gameplay data directly. The scroll inventory is independent of the crafting UI.

## Established Design Rules (do not change without asking)

- **Mana never regenerates naturally.** Each spell has its own pool. A depleted spell can't be cast until something explicitly restores mana (potions, debug tools, or future effects). Spells must not cast with insufficient mana.
- Crafting needs at least one Base and exactly one Area. Buffs are optional. Every buff and every increase in range or area raises mana cost. Hybrid (multi-Base) spells drain mana faster.
- Elements: Fire > Land > Thunder > Sea > Fire. Each element is strong against the one it beats and weak against the one that beats it. Enemies without an affinity take normal damage.
- XP feeds a permanent 20-level wizard track (reward table in the README). Gold buys equipment between runs. Spell slots go from 1 to 5.
- Inputs go through the Godot Input Map using logical actions. Keyboard, mouse, and controller share one gameplay implementation (WASD, E interact, 1–5 spell slots, mouse aim, LMB cast, Esc pause, M mute).

## Conventions

- Naming: PascalCase classes. snake_case variables, functions, and signals. UPPER_SNAKE_CASE constants.
- Use typed GDScript where practical. One responsibility per script. Prefer composition over inheritance. Avoid circular dependencies. Use signals between independent systems.
- Gameplay and balance values belong in Resources or `@export` properties, not scattered through scripts.
- Directories from the proposed layout (`scenes/`, `scripts/{autoload,systems,utilities}/`, `resources/`, `assets/`, `tests/`) are created only as their systems are built.
- Don't optimize prematurely. Profile first. Object pooling for projectiles is the likely first optimization.
- Record significant architectural decisions. The layout in `technical-design.md` mentions a `development-log.md`, which doesn't exist yet.

## Combat architecture (Sprint 1)

- Combat is built from small components on an entity: `HealthComponent`, `HurtboxComponent` (receives hits, optional player-wide invulnerability window), `HitboxComponent` (deals damage, per-target cooldown, optional one-shot), `KnockbackComponent`, `HitFlashComponent`. All damage goes through `DamageSystem.calculate`, the single place elemental rules will live.
- Collision layers (named in `project.godot`, bit constants in `PhysicsLayers`): world, player_hurtbox, enemy_hurtbox, enemy_hitbox, player_projectile. Enemy hurtboxes and hitboxes are passive (`monitoring = false`), so only the player's hurtbox and projectiles do any overlap work. Enemies never detect each other.
- Enemies are light `Node2D`s moved by position (no `move_and_slide()`), clamped to the arena bounds. Since Sprint 12b they also stay out of obstacles and route around them (see Obstacles). Stats come from `EnemyData` and spawning from `SpawnConfig`. The health bar and spell bar got the Sprint 13d look (see Interface).
- Aim and fire go through `AimComponent` (mouse, right stick, or the touch aim stick) and `cast`. The Player forwards both to `SpellLoadout`. `emulate_mouse_from_touch` is off on purpose, so touching the move stick never fires.
- Hand-written `.tscn` files need `node_paths=PackedStringArray("prop")` on the `[node]` line for any exported Node-typed property set with a NodePath, or it stays null silently.
- `TouchJoystick` is ours. Godot 4.7 has a native `VirtualJoystick`, so don't reuse that name.

## Spell architecture (Sprint 2)

- `SpellData` (Resource) is static configuration: elements, damage, mana, cast interval, projectile stats, `max_hits`. `SpellInstance` (`RefCounted`) is the equipped runtime object and owns current mana and the cooldown. Never put mutable state on `SpellData`, because resources are shared and two copies of a spell must never share mana.
- `SpellLoadout` (component on the Player) holds five slots and the selected index, selects and cycles, and casts through `try_cast`. A depleted spell stays selected and does nothing (no auto-switch). Slot keys, controller shoulder buttons (`spell_prev`/`spell_next`) and the touch `SpellBar` all end in `select` or `cycle`. `try_cast` instantiates the spell's Area scene (see Sprint 3 below).
- `MissileArea` takes everything from the `SpellData` it is launched with. `HitboxComponent.max_hits` and `SpellData.max_hits` make piercing a data change.
- Elemental math lives only in `ElementTable` (configurable multipliers, Fire > Land > Thunder > Sea > Fire) and `DamageSystem.calculate(base, attacker_element, defender_element, table)`. Since Sprint 4 the multiplier is applied at impact (see Elemental enemies below).
- `SpellBar` and `SpellSlotWidget` are the spell bar. Slot widgets read the loadout and handle touch taps themselves (`emulate_mouse_from_touch` is off) and ignore mouse clicks. F9 (`debug_restore_mana`, handled in `Main`) refills mana for testing.

## Area architecture (Sprint 3)

- Five Areas: Line, Cone, Area (ground zone), Missile, Wave. Each is its own scene under `scenes/spells/areas/`, whose root script extends `AreaEffect` and implements `launch(spell, origin, direction, target)`. `SpellLoadout.try_cast` instantiates `spell.area_data.scene` and calls it. Never branch on the Area type in the loadout, player or damage code.
- `AreaData` (Resource, `resources/spells/areas/`) holds one Area type's scene and defaults: `default_range`, `default_size`, `duration`, `tick_interval`, `widen_rate`, `needs_ground_target`. A `SpellData` points at one and carries `range_scale` and `size_scale`. `effective_range()` and `effective_size()` are the numbers every Area reads, and Sprint 6 crafting only has to write the two scales. Mana cost stays an authored number per spell. The rule "longer range costs more" belongs to the Spell Builder (Sprint 6), not the Areas.
- Ground-targeted Areas land at `SpellData.clamp_target(origin, target)`. The mouse's target is the cursor and a stick's is a far point along the aim, so a stick lands at full range. Targeting and the `TargetReticle` read `AreaData.needs_ground_target`.
- All Areas build their hit damage through `AreaEffect._configure_hitbox`, so Sprint 4 moves the elemental multiplier to hit time in one place. Line, Cone and Wave hit each enemy once per cast and Area hits once per tick, through `HitboxComponent.hit_cooldown`.
- Enemies are clamped to the arena bounds (no negative coordinates), so Area tests cast from an offset origin.

## Elemental enemies (Sprint 4)

- The elemental multiplier is applied when a hit lands. `HitboxComponent.element` is the attacker's element (set from the spell in `AreaEffect._configure_hitbox`, which carries raw damage) and `HurtboxComponent.element` is the defender's. `HurtboxComponent.receive_hit(damage, source_position, knockback, attacker_element)` gets the final damage from `DamageSystem.calculate` and an `ElementTable.Effect` (NEUTRAL, VULNERABLE, RESISTED) from `DamageSystem.effect`, then emits `hit_received(damage, source_position, knockback, effect)`. No other code does elemental math.
- Rules: an enemy has one element. It takes the strong multiplier from the element that beats it and the weak one from the element it beats. Same element, no element, or an unknown value is normal damage.
- The player's hurtbox has no element by default and enemy contact hitboxes carry none, so hits on the player are neutral. This is today's default, not a rule: equipment (robes, hats) may later give the player an element through `HurtboxComponent.element`, so never hardcode "the player is neutral".
- `EnemyData` is the composed shape an enemy runs on (element, colour, stats, rewards, behaviour). Since Sprint 11 it is built from an archetype and an element (see Enemies and bosses below), not hand-written per enemy. There is still one enemy scene. The five old enemy files live on only as test fixtures in `tests/fixtures/enemies/` (enemies with a known element and health).
- `Enemy.damaged(position, amount, effect)` is re-emitted by `EnemySpawner.enemy_damaged`, and `Main` routes it to `DamageNumbers`, a pooled node that draws every number in one `_draw`. Vulnerable hits are yellow and end in "!", resisted hits grey; all use the one font size (Sprint 13d).

## Scrolls (Sprint 5)

- `ScrollData` is one class with a category (BASE, AREA, BUFF), a rarity, a placeholder colour, and optional category fields: `element` (Base), `area_data` (Area, the Sprint 3 `AreaData`), `buff_id` and `buff` (Buff, its `BuffEffect`, Sprint 7). The 15 scrolls live in `resources/scrolls/{base,area,buff}/`. Adding a scroll is a new `.tres` plus a drop-table entry, with no code change. The inventory, drop tables and crafting only ever hold `ScrollData`.
- Drops: `EnemyData.drop_table` (a `DropTable` of `DropEntry` scroll and weight pairs, plus `drop_chance`). `DropTable.roll(rng)` never picks null, scroll-less or zero-weight entries. Tables are themed and belong to the enemy elements (`resources/enemies/elements/`): an elemental enemy weights its own element's Base scroll 12 and the other Bases 1, so it is heavily preferred but never guaranteed. Enemies carry data only. `EnemySpawner.enemy_died` is re-emitted, `Main` routes it to `ScrollDropper`, which rolls the table and places a pickup. The cap is 100 pickups, and a new drop removes the oldest.
- Pickups: `ScrollPickup` is a passive `Area2D` on layer 6 (`PhysicsLayers.PICKUP`), shaped by category (round Base, square Area, diamond Buff). One `PickupCollector` on the Player is the only active detector. Collection is automatic, a pickup can only be collected once, and a dead player collects nothing.
- `ScrollInventory` is a component on the Player (per run, stacks by scroll id, no limit): `add`, `remove` (all or nothing), `count`, `has`, `by_category`, `total_count`, and a `changed` signal. Crafting (Sprint 6) reads and consumes it through those methods.
- `ScrollToast`, `InventoryPanel` (key `I`, controller button Y) and `InventoryButton` are the scroll HUD. Since Sprint 15a the panel pauses the game while it is open (the user's request; it used to run live) and closes itself on I, pause or Esc. F10 (`debug_give_scrolls`, handled in `Main`, DEBUG) gives 3 of every scroll.

## Crafting (Sprint 6)

- The player starts with one spell (Fire Missile, a 1000-cast pool) and four locked slots. `SpellLoadout.unlocked_slots` (5 by default, 1 on the player) says how many slots can be used. `equip(index, spell_data)` puts a fresh full-mana `SpellInstance` in an unlocked slot and emits `slot_changed`. `unlock_next()` unlocks one more slot and emits `slot_unlocked` (levels call it, see Progression below). `select` and `cycle` skip locked slots, and the `SpellBar` dims them and follows a slot when its spell is replaced.
- **All crafting rules live in two static classes.** `SpellBuilder.build(base, area, option)` makes a `SpellData`: damage, interval, speed and knockback are the Area's baseline (`AreaData.base_stats`, an `AreaStats`) times the Base scroll's multiplier (`ScrollData.modifiers`, a `BaseModifiers`). Mana cost is also times the range option's cost multiplier, and the mana pool is not, so a longer range gives fewer casts. `CraftingSystem.validate/craft/preview` check a `CraftingRequest`, consume exactly one Base and one Area scroll all-or-nothing (a failed craft never touches the inventory or loadout), and equip the spell. Fire plus Missile at Normal range equals `fire_missile.tres` in every number except the pool: the starting spell has a generous 1000, while a crafted spell uses the Area baseline of 100. Range options (Short, Normal, Long, Very long) are in `resources/crafting/crafting_rules.tres`. Nothing is hand-written per Base and Area pair.
- Buffs became real in Sprint 7 (below). Size is not chosen at crafting, only range.
- `CraftingSession` (no UI) holds the screen's choices and previews. `CraftingScreen` is a thin layer over it and holds no rules. It works with mouse, keyboard or controller focus, and touch through `TouchBridge`, because `emulate_mouse_from_touch` is off. The bridged click goes straight into the viewport with `push_input` (not `Input.parse_input_event`, which would scale the position twice and press the global `cast` action).
- **Pause.** Opening the screen pauses the scene tree (`CraftingScreen` has `process_mode = Always`) through `GamePause.set_paused`, which also freezes `GameTime`, a clock that stands still while paused. `HitboxComponent.try_hit` reads `GameTime.now_msec()`, so hit cooldowns survive a pause. `Main` resets `GameTime` on load. After the screen closes, `Player.require_cast_release()` keeps the player from casting until the cast input is released once (it reads the real input, because `aim.is_firing` is stale on the first frame after a pause).
- **Lecterns** are passive `Area2D`s on layer 7 (`PhysicsLayers.INTERACTABLE`) in the group `lecterns`. They hold no crafting logic and only emit `interacted`. The Player's `InteractionComponent` tracks the nearest one in range, shows its prompt, and `interact` (E, controller A) or the touch `InteractButton` uses it. A dead player cannot interact. Three Lecterns are placed by the map data (see World and maps below), far apart. They are reusable, unlimited and free.
- F8 (`debug_give_potions`, 3 of every potion for this run, not saved), F10 (`debug_give_scrolls`), F12 (`debug_give_xp`, 100 XP, saved like real XP) and F9 (`debug_restore_mana`) are DEBUG keys handled in `Main`, to delete when their real systems exist.

## Buffs (Sprint 7)

- A buff is data: `BuffEffect` (`resources/crafting/buff_effect.gd`) on the Buff scroll holds `damage_multiplier`, `max_mana_multiplier`, `cost_multiplier`, `vulnerability_bonus`, `ignores_resistance`, `extra_copies`, `extra_bases` and `max_stacks` (0 means none). The six effects are in `resources/crafting/buff_effects/`. A repeated scroll in a request is a stack. Multipliers multiply, bonuses add, and no buff is hardcoded by name anywhere.
- `SpellBuilder.build(bases, area, option, buffs)` averages the Bases' multipliers (a hybrid), then applies each stack. Every stack raises the cost at least as fast as it raises damage or copies, so damage per mana never improves. Increased Max Mana is the deliberate exception. `SpellBuilder.can_cast(spell)` is false when the cost is above the pool, and `CraftingSystem` then refuses with `REASON_TOO_COSTLY`.
- `CraftingRequest.bases` is a list. The count must equal 1 plus the Additional Base stacks, with no repeated element, and stacks respect `max_stacks`. `CraftingSystem` checks the whole recipe and the owned quantities first and only then consumes every scroll, so a failed craft still changes nothing.
- A `SpellData` carries `copies`, `vulnerability_scale`, `ignores_resistance` and `buff_stacks`. Its `attack_profile()` (cached, so call it once the spell is built) is what a hit carries. `HurtboxComponent.receive_hit` resolves it through `DamageSystem.resolve`.
- `CastPattern.shots(spell, origin, direction, target)` returns one `CastShot` per copy (a ring around the player, or a ring of zones around the target), and `SpellLoadout.try_cast` launches one effect per shot for a single mana payment. Areas know nothing about copies.
- `CraftingSession` holds `bases`, `buffs` (stacks), `max_bases()`, `add_buff`, `remove_buff`, `can_add_buff` and `drawbacks()`. `CraftingScreen` shows a buff row with steppers, the Base heading "Base (n of N)" and the drawbacks.

## Progression (Sprint 8)

- XP and level are **permanent**. Everyone starts at level 1, which gives nothing. `LevelTrack` (`resources/progression/level_track.tres`) holds the XP curve, the 19 `LevelReward`s for levels 2 to 20 (SPEED, HEALTH, MANA, SLOT, RANDOM_BUFF, CHOSEN_BUFF, SECOND_SPELL) and the `buff_pool`. All of it is data, and no code branches on a level number or a buff id. The level is always computed from `PlayerProfile.total_xp`.
- **Saving.** `PlayerProfile` (total XP, Gold, owned and equipped items) is written by the static `SaveGame` as versioned JSON in `user://save.json` (outside the repo, in Godot's per-project user-data folder), through a temporary file and a rename. A missing file is a fresh profile, and a file that cannot be used is renamed to `.bak` and never deleted. `ProfileSaver` saves on request, every 10 s while dirty, and on close, focus loss and app pause. To reset progress, delete the one file.
- **Tests never touch the real save.** `SaveGame` calls take a path, and tests use a folder inside `res://.godot/save_tests/` that they create and remove. `Main.save_path` defaults to the real file, and an empty string means "do not load or save", so every test that instantiates `main.tscn` sets it (and the pick screen's `pause_tree` to false) before `add_child`.
- **When rewards apply.** Stat and slot rewards apply at once, through `RunProgress` (a Player component that turns collected XP into level-ups). Starting-spell rewards apply at the next run start. `Player.apply_stat_bonuses(StatBonuses, heal_difference)` is the one stat path: it computes speed, maximum health and the spells' mana bonus from the player's base values, so applying twice is harmless (Sprint 9 equipment will feed the same `StatBonuses`). The mana bonus lives on each `SpellInstance` (`max_mana()`), never on a shared `SpellData`, so read a pool through `max_mana()`.
- **Run start.** `Main._begin_progression` loads the profile, rolls every earned random buff (`StartingBuffs.roll_random`) and asks for each earned chosen buff on `BuffPickScreen` (the world is paused meanwhile), into an in-memory `RunBuffs`. **Starting-spell buffs are never saved: they are rolled or picked again at every run start** (player feedback). Then `RunStart.prepare` sets stats, slots, equipment bonuses and the two starting spells (`SpellBuilder.with_buffs` returns a copy with the buffs folded in, so the shared spell resources are never changed). The pool leaves out Additional Base, because a starting spell has no second Base.
- **XP gems and Gold coins.** `EnemyData.xp_reward` and `gold_reward`, one `ValueGem` pickup (kind XP or GOLD, collected by the same `PickupCollector`, which emits `xp_collected` or `gold_collected`) and one `ValueDropper` per kind (capped at 150, merging a new drop into the oldest at the cap so nothing is lost). The XP bar, Gold counter, level toast and the death screen's summary line have the Sprint 13d look.

## Gold and equipment (Sprint 9)

- **Gold** is banked in `PlayerProfile.gold` the moment a coin is collected (`RunProgress.add_gold`) and saved like XP. Dying never costs it.
- **One modifier path.** Level rewards and equipped items both add into one `StatBonuses` (`StatBonuses.combined`), pushed by `Player.apply_stat_bonuses` to speed, health and `SpellLoadout.set_bonuses`. `RunStart.prepare` and `RunProgress._apply` both use level plus `ShopSystem.bonuses`, so a level-up never drops equipment and nothing applies twice. The stats are SPEED, HEALTH, SPELL_MANA, the four element damages, SPELL_DAMAGE, CAST_SPEED and the two chance effects.
- **Casting.** Static `CastMath` holds the formulas (damage scale = spell damage times the mean of the spell's element bonuses, floored at 0.1; interval = base / (1 + casting speed), floored at 0.05 s; pool). `SpellLoadout.try_cast` sets `AreaEffect.damage_scale` on each effect before `launch` (the one multiplication is in `AreaEffect._configure_hitbox`), so no Area and no shared `SpellData` is edited. `SpellInstance` carries `cast_speed_bonus` and `max_mana_bonus` (per instance). Wand "cast twice" launches every shot a second time for the same mana and cooldown, and Staff "double damage" doubles every shot, each rolled once per cast from `SpellLoadout.rng`. `SpellBuilder.describe(spell, bonuses)` and the crafting preview use the same math.
- **Equipment is data:** `EquipmentData` (id, name, description, category, price, `EquipmentModifier` list, colour) in an `EquipmentCatalog` (`resources/equipment/`). Three slots: Robe, Weapon (Wand or Staff) and Headwear (Hat or Hood, identical behaviour). Adding an item is a new `.tres` plus a catalog entry. No code branches on an item id.
- **Shop.** The static `ShopSystem` holds all the rules (`buy` is all-or-nothing and equips into the item's slot, `equip` and `unequip` are free, `bonuses` skips unknown, unowned or misplaced ids). `ShopScreen` is a thin layer over it, opened by the death screen's Shop button, and every successful action is saved at once. Pressing an item buys, equips or takes it off depending on what the player has.
- **Death-screen taps.** Touches never reach buttons (mouse emulation is off), so `DeathScreen.handle_event` handles a tap on the Shop button itself (it requests the shop and never restarts), ignores every restart while the shop is open (`set_shop_open`), and still restarts on a tap anywhere else. This was checked on a real window, not only headless.
- Tests that instantiate `main.tscn` set `save_path` and never touch the real save, as in Sprint 8.

## Potions (Sprint 10)

- **Potions are data:** `PotionData` (id, name, description, price, `kind` HEAL / RESTORE_MANA / TIMED_BONUS / INVULNERABILITY, magnitude, duration, cooldown, `EquipmentModifier`s, colour) in a `PotionCatalog` (`resources/potions/`, bar order). No code branches on a potion id. Adding a potion of an existing kind is a new `.tres` plus a catalog entry.
- **Stock (Sprint 14b: potions last ONE run, user decision).** `RunPotions` (`scripts/potions/`, in memory, never saved) holds at most `MAX_POTIONS` = 3 of each type; `Main` makes a fresh one at every run start, so unused potions are lost when the run ends. The in-run merchant is the only source: the death-screen shop has no Potions row and `PlayerProfile` no longer holds potions. Buying is `ShopSystem.buy_potion(profile, potions, catalog, id, multiplier)` (Gold from the profile, the count and cap from `RunPotions`, all or nothing). A drink saves nothing; a merchant sale saves the Gold spent. An old save's potions load into `PlayerProfile.legacy_potions` (a count above 99 is a bad save), are cashed in at list price by `ShopSystem.cash_in_legacy_potions` at run start, and the save is rewritten without them.
- **Drinking.** Static `PotionSystem` holds the rules: `refusal` returns why a potion can't be drunk (checked in a fixed order: unknown, dead, none left, type cooldown, shared cooldown, effect running, full health, full mana) and `apply` does the effect. A refused potion is never consumed and starts no cooldown. `PotionBelt` (Player component) drinks through it, keeps each type's cooldown and the 1 s shared cooldown, and holds the controller's selection. Cooldowns and effect timers tick in `_process`, so they freeze while the tree is paused.
- **Timed effects.** `ActiveEffects` (Player component) keeps the running TIMED_BONUS and INVULNERABILITY effects and owns the player's temporary bonus layer. Invulnerability also grants the hurtbox a separate window (`HurtboxComponent.grant_invulnerability`) that the per-hit window can neither shorten nor clear.
- **Stat layers.** The Player holds `level_bonuses`, `equipment_bonuses` and `temporary_bonuses`. Each owner sets its own layer (`RunStart` and `RunProgress` the level one, `RunStart` the equipment one, `ActiveEffects` the temporary one) and calls `Player.refresh_bonuses()`, which adds the three, pushes the total through `apply_stat_bonuses` and emits `bonuses_changed`. Nothing else pushes bonuses.
- **Luck** is a `StatBonuses` stat. `DropTable.roll(rng, luck)` multiplies a scroll's weight by `rarity_factor` (Common 1, Uncommon 1 + luck, Rare 1 + 2 x luck, never below 0; falls back to luck 0 if every weight would be zero), and `Main` keeps `ScrollDropper.luck` in step with `bonuses_changed`. At luck 0 the roll is exactly the old one.
- **The potion bar** (`PotionBar`, `PotionSlotWidget`) is a column of six slots at the top right. Slots handle their own touches and left clicks (mouse emulation is off), and `Main` blocks casting until the cast input is released so a click never also fires a spell. Keys Z X C V B N (`potion_1` to `potion_6`), controller X, left stick click and B (`potion_next`, `potion_prev`, `potion_use`; the D-pad is movement, and a test fails if any joypad button belongs to two gameplay actions). A refusal shows its reason in the level toast's message line. The bar hides on death.
- Checked on a real window (3x scale) with a throwaway profile: a tap or a mouse click on a slot drinks exactly once and fires no spell.

## Enemies and bosses (Sprint 11)

- **An enemy is an archetype plus an element, picked independently by weight (user decision, "mix and match").** `EnemyArchetype` (`resources/enemies/archetypes/`: Standard, Swarmer, Chaser, Tank, Ranged, Exploder, Support) holds every stat, the body size, the behaviour (`EnemyBehaviorData`), the unlock time, the cluster size and the drop-chance scale. `EnemyElement` (`resources/enemies/elements/`: none, Fire, Thunder, Land, Sea) holds only the affinity, the colour and the themed drop table. **An element never changes a stat**: a Thunder Tank is as tough as a Land Tank. `EnemyComposer` builds one cached, shared `EnemyData` per pair (names like "Thunder Tank").
- **Shared data is never edited.** Per-spawn values live on the `Enemy` instance: `apply_scales` (difficulty) and `make_elite(EliteModifier)` (x3 health, x1.5 damage, x1.15 speed, x1.4 size, x3 rewards, x2 drop chance, an outline), both worked out from base values so they never compound. `xp_reward()`, `gold_reward()` and `drop_chance_scale()` are what the droppers read, and `gives_rewards` is false for an Exploder that blasted itself.
- **Behaviour is a brain, chosen by the archetype's kind.** `EnemyBrain.for_data` gives `BrainChase` (the old movement), `BrainKeepDistance` (Ranged: holds about 90 px and fires `EnemyProjectile`s), `BrainExplode` (stops, fuses with a `BlastZone`, dies in its blast with no rewards, and the blast is cancelled if the player kills it first) or `BrainSupport` (heals other enemies in range every 0.25 s). Nothing branches on an enemy name.
- **Telegraph rule.** `EnemyProjectile` (cap 60) and `BlastZone` (cap 40) are shared by enemies and the boss. A blast zone is harmless until its fuse ends, never moves, checks the player once, and counts `_process` deltas so it freezes while paused. Every boss attack has a warning.
- **Difficulty.** `DifficultyCurve` (`resources/enemies/difficulty_curve.tres`) maps run seconds to health, damage and speed scales, the spawn interval, the maximum alive, the elite chance and the boss interval. `RunClock` (static) is the pausable run clock: it reads `GameTime` from a start marker that `Main` resets (`GameTime.reset()` alone does not zero it). The spawner unlocks archetypes by time, spawns Swarmer clusters, and `spawn_rate_scale` halves spawning while a boss lives.
- **Bosses are data.** `BossData` (phases, rewards) with `BossPhase` (a health threshold, an attack list, an interval, a speed multiplier) and `BossAttack` (SLAM, CHARGE, BURST, SUMMON with their numbers). `Boss` is one state machine (IDLE, TELEGRAPH, ACT, RECOVER) that runs any `BossData`: it ignores knockback, stays in the arena, takes +50% damage after a charge, and a hit that skips a phase lands in the last one it reached. `RunDirector` spawns a boss at 300 s and 300 s after the previous one spawned (never two at once), cycles the roster, scales each boss by its number and pays XP, Gold (both times the number) and Rare scrolls where it died. The run continues after a boss (user decision).
- **Stress.** The stress scene starts the clock at `--minutes` (default 5), has `--boss`, and keeps its enemy count with `spawn_at(position, cluster_limit)`.

## World and maps (Sprint 12a)

- **A map is data.** `MapData` (`resources/maps/`) holds the size, colours, player start, `spawn_config` (null keeps the scene's), `placements` (`MapPlacement`: a scene and a position) and the decoration scatter fields. `problems()` lists faults. The first map is `first_map.tres`: 1920×1080, start (960, 540), three Lecterns at least 700 px apart. Nothing branches on a map id.
- **`GameMap`** (`scenes/world/game_map.tscn`) builds the `Border` and `Floor` rects, the four boundary walls (static bodies on the world layer, closed at the corners), the `Decor` layer, the `Placements` and a hidden `Debug` overlay from its `map_data`. It replaced `test_arena.tscn` in `main.tscn`. `test_arena.tscn` stays only for the stress scene, so the stress numbers stay comparable.
- **`Main._apply_map` is the only place the arena size is read:** it sets `EnemySpawner.arena_bounds`, the spawner's config (when the map has one), the player's start and the camera limits. The `Rect2(0, 0, 960, 540)` defaults in `EnemySpawner`, `Enemy` and `Boss`, and the tests' own bounds, are only defaults.
- **Decorations** are `MapDecor.scatter(map)`: seeded, deterministic, clear of the player start and every placement, and it always ends. `MapDecorLayer` draws them in one `_draw` (TEMPORARY look).
- **F7** (`debug_toggle_map`, handled in `Main`, DEBUG) toggles `MapDebugOverlay` (bounds, start, a labelled marker per placement). Sprints 12b and 12c add obstacles and points of interest as more placements and data.
- Obstacles (Sprint 12b, below) are placements-in-data too: `MapData.obstacles`.

## Obstacles (Sprint 12b)

- **What obstacles block (user decision):** movement (the player's and every enemy's) and enemy projectiles. **Every player spell passes over them**, so no Area and no damage code knows about obstacles. Blast zones and boss slams are ground effects and ignore them. Missile blocking was considered and rejected.
- **Data.** `MapObstacle` (`resources/maps/`): RECT (centre, full size) or CIRCLE (centre, radius), with exact `contains`, `overlaps_rect` and `blocks_segment`. `MapData.obstacles`, `nav_cell_size` (16) and `body_clearance` (8) hold them. `MapData.problems()` checks shapes (valid, inside the map, 24 px from the start and every placement). **Reachability is `ObstacleGrid.reachability_problems(map)`, not `problems()`** (the grid is built from `MapData`, so the other way round would be a circular dependency), and `GameMap` reports both with `push_error`.
- **`ObstacleGrid`** is a coarse byte grid: a cell is blocked when an obstacle grown by the body clearance touches it, and cells outside the map count as blocked. **`FlowField`** sweeps outward from the player over the free cells (Dial's algorithm, the 16 moves of the 5x5 chamfer, never cutting a blocked cell) and each cell's direction is the pull of its lower neighbours. When two routes tie, or the blended direction would point into a blocked cell, the single best neighbour is used (found by the U-shaped dead-end test: the symmetric tie jammed enemies on the axis). Directions are cached per cell until the next field is swapped in.
- **The sweep is incremental.** A whole sweep of the first map takes about 33 ms, so `FlowField.begin_rebuild` and `advance(cell_budget)` do it in pieces (about 400 cells, 1.8 ms, a frame; 19 frames, so the field lags the player by about 0.3 s) and the finished field replaces the old one all at once. `ObstacleMap` starts a rebuild when the player enters a new cell and at least 0.2 s have passed since the last one began. Physics frames stop while paused, so nothing advances then.
- **`ObstacleMap`** (a node under `GameMap`, in the group `obstacle_map`) owns the grid and the field and answers `direction_from`, `is_blocked`, `blocks_segment` (exact against the shapes, with a quick all-cells-free shortcut for short segments), `push_out` and `resolve_move` (the move, else the free axis, else stay). **With no `ObstacleMap` in the tree every caller behaves as before**, which is why older tests did not change. `GameMap` also builds a `StaticBody2D` per obstacle on the world layer (the player collides through physics with the same shapes) and an `ObstacleLayer` that draws them in one `_draw` (TEMPORARY look).
- **Who uses it.** `Enemy.direction_to_target` follows the field (keeping the horde-spreading offset as a sideways nudge) and `_physics_process` moves through `resolve_move`, so Chase, Ranged's approach, the Exploder and Support all route with no brain edited. The one brain that checks a line is Ranged (`Enemy.has_clear_line_to`): behind a wall it keeps approaching through the field and does not fire, instead of holding its distance (found in the review: it parked behind walls). A knocked-back or spawned-inside enemy is pushed out on its next step. The `Boss` walks the same field, and a Charge that hits an obstacle ends at once (the recovery and the vulnerability window still follow). `EnemyProjectile` frees itself when its step crosses an obstacle. `EnemySpawner` rejects blocked ring points and pushes every spawned enemy, cluster member, summon and boss out of obstacles.
- **Layout limits** (tested in `tests/test_first_map_layout.gd`; Sprint 12c widened the counts, see Map regions below): at the time 25 to 35 obstacles, the outer 48 px band free, a 150 px open area around the start, 3% to 25% of cells blocked, no gap narrower than two cells (16 px cells and an 8 px clearance can turn a 48 px corridor into one free cell, so corridor walls are 80 px apart centre to centre and off the grid), at least one open 10 by 10 cell square 400 px from the start. Every Lectern is judged by eye to have two routes.
- **F7** also draws the obstacle outlines, the blocked cells and the field's arrows near the player. `--obstacles` on the stress scene uses the first map.

- **Near the player, bodies use exact walls and the real player position (two bug fixes during Sprint 12c).** The grid keeps bodies 8 to 24 px off walls (the clearance plus rounding to 16 px cells) and the flow field is built from where the player was a moment ago (it rebuilds over about 0.3 s), but the player stands 6 px from walls and moves every frame. Two exploits came from that: hiding in the corner of two walls (or pressed against a thin wall), and hugging a corridor wall while running back and forth (enemies followed the field down the middle, chasing where the player had been). So within `ObstacleMap.NEAR_RANGE` (160 px) of the player: `Enemy.direction_to_target` and the boss steer straight at the player when `ObstacleMap.line_clear` says a body can walk the line (the grid answers most lines, a line through a blocked cell is checked against the exact shapes grown by `MapData.body_radius`, 5 px, a little under half a body so a body flush against a wall is not blocked by a rounding error), and `resolve_move` lets a body enter a blocked cell if it does not overlap an exact wall (`ObstacleMap.overlaps_wall`). Beyond it, and with no clear line, the field routes as before, and a body inside a blocked cell uses the direction of the nearest free cell (`direction_from`), so it never pushes straight at a wall. **The invariant to keep: the player can only stand where an enemy can reach, and the field is only for routing.**

## Map regions (Sprint 12c)

- **`MapMaze`** (`resources/maps/`) generates a maze from data: `area`, `cell_size` (80, wall centre to wall centre, so a 16 px wall leaves a 64 px gap), `wall_thickness`, `maze_seed`, `entrances` (`MazeEntrance`: a boundary cell and an `Edge`), `extra_openings` (walls removed after generating, for loops) and `clear_center` (opens the middle 2 by 2 cells). It is an iterative recursive backtracker with a local seeded `RandomNumberGenerator`, so the same data always gives the same walls, in the same order. `shapes()` returns RECT obstacles. `MazeEntrance.Edge` is not called `Side` because that is a Godot global enum. The seed field is `maze_seed`, because `seed` shadows a built-in function.
- **`MapData.solid_shapes()` is the one list of solid things**: the authored `obstacles` plus every maze's walls, built fresh on each call. `ObstacleGrid.build`, `GameMap` (the drawn layer and the physics bodies), `ObstacleMap` (it keeps the list from `setup`), `MapDebugOverlay`, `MapDecor` and `MapData.problems()` all read it, and nothing else knows mazes exist. `problems()` reports a bad maze or zone and skips the shape checks of a maze that already has problems, so one fault is one line.
- **`MapZone`** is a region with a floor tint and its own decorations (no gameplay effect yet). `GameMap` draws a `Zones` node (one `ColorRect` per zone, ignoring touches) above `Floor` and below `Decor`. `MapDecor.scatter` and `scatter_zone` keep every decoration off the player start, the placements and every solid shape (2 px margin).
- **The first map** is still 1920x1080, laid out in a 3x3 grid of regions of about 640x360: **two 9x6 cell mazes in opposite corners** (north-west `Rect2(60, 60, 720, 480)`, south-east `Rect2(1140, 540, 720, 480)`; the second has the same data with `rotated = true`, so it is an exact half-turn image of the first), each with entrances on three sides, 3 extra openings and a cleared centre room (`MapMaze.center_room_center()` gives its middle, which follows the rotation), a walled island in the north-east (about 360x280, a gate south and a gate west, each 80 px, an empty interior), a 560 px corridor along the bottom, the open plaza between the mazes and pillar groves. The three Lecterns are outside the mazes and the island. Each maze's centre room and the island's interior are left empty for Sprint 12d.
- **Performance work found by profiling** (Sprint 12c, two mazes): `MapMaze.shapes()` merges walls that continue along one line into one rectangle (the same area, about 40% fewer shapes: physics bodies, grid build and shape tests all scale with the count), and `MapDecorLayer` and `ObstacleLayer` draw in 512 px `DrawChunk` nodes so the engine skips the ones off screen (one big node was drawn whole every frame, about 3 ms). `item_count()` is still the total.
- **Layout tests** (`test_first_map_layout.gd`, `test_first_map_regions.gd`): 50 to 220 solid shapes, the outer 48 px band and a 150 px area around the start free, 3% to 40% of cells blocked, no gap narrower than two cells, **every free cell reachable from the start**, an open 10 by 10 cell square 400 px from the start. Coordinates sit off the 16 px grid on purpose (the mazes sit at (60, 60) and (1140, 540)), because a bad alignment turns a 48 px corridor into one free cell.

## Points of interest (Sprint 12d)

- **One generic node, driven by data.** `PointOfInterestData` (`resources/points_of_interest/`) has a `kind` (HEAL, RESTORE_MANA, LOOT, MERCHANT) and numbers (`amount`, `gold_min` and `gold_max`, `scroll_count` and `scroll_table`, `stock_per_potion`, `price_multiplier`, `refresh_seconds`, `color`). A Rare scroll spot is a LOOT with no Gold and the Rare-only table (`resources/bosses/boss_scrolls.tres`), the chest uses `resources/drops/chest_drops.tres` (all 15 scrolls, weighted 6, 3 and 1 by rarity). No code branches on an id. `PointOfInterest` (an `Area2D` on the interactable layer, group `points_of_interest`, five small scenes in `scenes/interactables/`) only holds the prompt, a refresh timer counted in `_process` (so it freezes while paused and starts ready every run, nothing is saved) and a ring, and emits `used`. Anything with an `interact` method is found by the player's `InteractionComponent`, so E, the controller's A and the Interact button all work.
- **Rules are static** (`PointOfInterestSystem`): `refusal(data, player, cooldown_left)` (dead, refreshing (never for a merchant), full health, every spell full) and `apply(data, player, rng, luck)` (heal or restore a fraction, or roll Gold and scrolls). A refused use changes nothing and starts no timer. `PotionSystem.all_spells_full` is public for the Mana Shrine.
- **`Main` routes a use** (`connect_point_of_interest`, `_on_point_used`): a refusal shows its reason in the level toast; a merchant opens the `MerchantScreen`; otherwise the effect is applied, Gold goes through `RunProgress.add_gold`, scrolls through `ScrollDropper.place` at `point.loot_spot(i, count)` (a 20 px ring) and the timer starts.
- **The merchant** sells potions only (user decision: scrolls do not persist, so a bought scroll could be lost by dying). `MerchantStock` (runtime only) holds the counts and refills them all, `refresh_seconds` after the first sale; its prompt reads "Merchant (E) 4:30" while potions are missing and the merchant screen shows "Restocks in 4:30" or "Fully stocked" (`MerchantStock.seconds_to_restock`; the world is paused while the screen is open, so it shows the time as of opening or the last sale). `ShopSystem.buy_potion` and `can_afford_potion` take a `price_multiplier` (1.5 for the merchant, rounded up) and stay all or nothing. `MerchantScreen` pauses the world like the crafting screen, handles its own touches, guards the press that opened it, and a purchase saves the Gold spent at once (`Main._on_merchant_purchase`), shows "own n/3" and says potions last one run. A headless test cannot deliver a click to its buttons (GUT's own panel is under the pointer), so the real click and touch were checked in a real window.
- **Placement on the first map (Sprint 14a moved them):** the Rare scroll spots (maze centres), the Health Shrine (corridor) and the Mana Shrine (island, now alone there) are unchanged. The chest is at (208, 944) in the bottom-left inside a ring of seven trees (opening east), the merchant at (1210, 384) inside a hedge yard with an 80 px gate on its west side, and the three Lecterns at (1024, 144) (a ring), (176, 688) (a ring) and (1744, 444) (a hedge room between the island's south wall and the south-east maze's top wall, gate on its west side). See World pass (Sprint 14a) below. The shrine near the map's bottom edge has its prompt hidden by the spell bar (the camera stops at the edge).

## Art pipeline (Sprint 13a)

- **Sources and outputs.** `art/palette.txt` has `color <letter> <hex>` lines (fixed colours) and `variant <id> <5 hex>` lines (the five ramp slots `1` to `5` of an element: body dark, mid, light, trim dark, trim light). `art/sprites/<name>.sprite` has `size w h`, `anim name first last fps loop|once`, then `frame` blocks of letter rows (`.` is clear). A sprite that uses ramp slots is built once per variant (`none`, `fire`, `thunder`, `land`, `sea`), others once as `base`, and every sprite also gets a white `_silhouette` sheet. `godot --headless -s tools/art/art_builder.gd` writes `assets/sprites/<name>_<variant>.png` (frames side by side) and a `SpriteSetData` `.tres` beside each; run `godot --headless --import` afterwards. Outputs are committed, so the game never needs the tool.
- **Code.** `ArtPalette` and `SpriteSource` parse, `ArtBuilder` builds, `SpriteLibrary.find(name, variant)` looks a set up (falling back to `base`), `SpriteSetData.frames()` builds and caches a `SpriteFrames`. Frame rates and loop flags live in the `.sprite` header, never in code.
- **`BodyView`** (a Node2D that builds its own `Outline`, `Sprite` and `Fallback` children) replaced the `Body` rectangle of the player, `Enemy` and `Boss`: `set_look`, `play`, `set_facing`, `set_tint`, `set_outline`, `counter_scale`, `fallback_color`. With no art it shows the old coloured square (`fallback_color`), so a missing sprite never crashes or hides an entity. The hit flash sets `modulate` and a tint sets the sprite's `self_modulate`, so they multiply and never fight.
- **1:1 rule.** The sprite is never scaled: `counter_scale(scale)` undoes the owner's scale (which sizes the 12 px hit shapes), so a Tank or the boss is a bigger drawing, not a stretched one. The sprite never decides collision.
- **Naming.** Enemies are `enemy_<archetype id>` in the element's variant (`EnemyData.element_id`, set by `EnemyComposer`), the boss is `boss_<boss id>`, the player is `player`. State animations: `move`, `death`, and one of `attack` (Ranged, 12 fps, once), `fuse` (Exploder, loop) or `pulse` (Support, once) per enemy, started through `Enemy.show_state(state, seconds)`. Boss: `idle`, `telegraph`, `attack`, `vulnerable`. A death animation frees the enemy once (with a 1 s safety timer).
- **Tests.** `tests/test_art_assets.gd` rebuilds every sprite in memory and fails if a committed PNG or `.tres` differs (pixels, and animation names, ranges, fps and loop), if a pixel is not a palette colour, if a frame touches its 1 px margin, if a set does not load, or if an output file belongs to no source or variant (an orphan would still be loaded, since `SpriteLibrary` tries the element's variant before `base`; delete it). Edit a `.sprite` and forget to run the tool, and it fails.
- **Replace art** by editing the grid and re-running the tool, or by drawing the sheet: overwrite its PNGs (same frame size and frame order) and add a `hand_drawn` line to the `.sprite` (`SpriteSource.hand_drawn`). The tool then never rebuilds that sprite's sheets, still writes its `.tres` from the header and makes its silhouette from the first sheet (`ArtBuilder.silhouette_of`), reports a missing sheet, and the asset test checks only the sheet size and the silhouette. Without the line the next tool run overwrites a drawn PNG and the pixel test fails. Checked in a real window: a recoloured sheet shows with no code change.
- **Performance.** Drawing 300 sprites costs about 30% of the stress frame rate against rectangles (about 139 against 199 fps with `--obstacles --drops`). Animation itself costs nothing measurable. A runtime shared texture atlas is the next lever if a slow device struggles. `BodyView._process` runs only while an outline is shown.

## World art (Sprint 13b)

- **The map names its art.** `MapObstacle.material` (`stone`, `hedge`, `tree` ...), `MapMaze.material` (stamped on every wall it generates), `MapZone.floor_style`, `MapData.floor_style` and `border_style`, and `decoration_styles` (on the map and on zones, used in place of the colours when set). `WorldArt` (static) resolves a name by one rule through `SpriteLibrary`: `tile_<style>`, `wall_<material>`, `post_<material>`, `decor_<style>` (base variant). **A name with no art is null and the caller keeps today's flat colour**, so a missing sprite never hides a wall or breaks a map. Nothing branches on a map, zone or material id.
- **Two new `.sprite` markers.** `tile` (full-bleed repeating tile: no transparent pixel, no 1 px margin rule, no silhouette) and `slice <left> <top> <right> <bottom>` (a tile's 9-slice margins in pixels, for walls), both carried into the `SpriteSetData` (`tile`, `slice`). The palette limit is 64 colours (was 40) with a world section.
- **Floors.** `GameMap` keeps its `Border`, `Floor` and `Zone_*` `ColorRect`s (the flat fallback colours) and adds `BaseArt` (the border and map `FloorPatch`es, hard-edged, before `Zones`) and `ZoneArt` (one soft `FloorPatch` per zone with a floor style, after `Zones`). A zone with floor art hides its flat tint (the node and its colour stay), because the soft edge must show the floor below, not a straight-edged rectangle. `FloorPatch` draws a tiled rectangle for its middle and, for a soft one, the outer 32 px in 8 px cells with how deep the gap reaches following smooth noise along the edge (wavy bays, never a straight line; the first version, a 16 px band with random cells, still read as a straight line). **The middle ends on the 8 px cell grid** (`interior_rect()`), because cutting it at "size minus 32" left a bare strip, where the grass showed, through every zone whose size is not a multiple of 8 (found in the review; `test_every_pixel_is_covered_once_for_any_size` pins it). **A stone zone is sized to its structure grown by at least 48 px**, so its wavy edge lies outside the walls and the floor inside is solid (the first map's maze zones are 832 by 592, the island 520 by 384, the tunnel 680 by 200).
- **Walls and posts.** `DrawChunk` draws a RECT obstacle as a 9-slice (`NineSlice`: corners 1:1, edges and centre tiled 1:1, never stretched) of its `wall_<material>` tile and a CIRCLE as its `post_<material>` sprite (one size, about 44 px, so a post can differ from its collision radius by up to about 4 px; collision stays authoritative). Corners and edges of every wall are drawn first and the centres second, **as two passes over the whole layer** (`ObstacleLayer`: the border chunks, then a `Centres` node of centres-only chunks after them; `chunks()` lists the border ones), so where walls cross there is no border line across the junction even when the two walls are in different 512 px chunks (a per-chunk second pass left 11 seams on the first map). An obstacle with no art keeps the grey fill. The layers stay chunked, so off-screen chunks cost nothing.
- **Decorations.** `MapDecor` items are `{rect, color, style, frame}`; `style` is empty without `decoration_styles`, and `frame` is a seeded whole number `DrawChunk` reduces modulo the sprite's variants, so `MapDecor` loads no art and stays deterministic. A map with no styles scatters exactly as before (a golden test pins it). **Decorations with styles are spread evenly**: for each one `CANDIDATES` (10) valid spots are tried and the one farthest from every decoration already placed is kept (a best-candidate scatter; random scatter left clumps and bare pockets, the user's feedback), and the map's own scatter skips any zone that has a `floor_style`, because that zone scatters its own.
- **Lectern, points of interest and pickups.** Each has a `Body` (`BodyView`) with the old shape kept as the fallback: the Lectern's `idle` glow, a point's `ready` and `used` (dimmed while refreshing; a merchant is never refreshing) from `PointOfInterestData.sprite_name`, scrolls by category (`scroll_base`, `scroll_area`, `scroll_buff`, white so the scroll's colour tints them, `sparkle` for Rare) and `pickup_xp` (blue, so it stands out on grass and stone) and `pickup_gold`. **A kill's drops never hide each other (user feedback):** pickups draw by value through `z_index` (a scroll 2, an XP gem 1, a coin 0), and `ValueDropper.drop_offset` (set in `main.tscn`: XP (-7, 3), Gold (7, 3), applied only in `on_enemy_died`, never in `place`) fans XP to the left and Gold to the right of where the scroll lands. The bob shader moves onto the sprite through `BodyView.set_sprite_material`. With art, a point draws only its ring and the old rectangles are drawn only when there is no sprite.
- **Shadows (user request): things that move, can be picked up or can be used have a soft oval shadow; static things (walls, trees, decorations) have none, so a player can tell them apart.** `BodyView.shadow_enabled` (set in the scenes of the player, enemies, boss, Lectern, points of interest and the three pickups) adds a `Shadow` sprite behind the sprite: the biggest of `shadow_8/12/16/24/32` no wider than the sprite, at its feet in world pixels (kept 1:1 under a scaled owner), 40% see-through, none without art. **Every shadow is drawn at one absolute depth, `BodyView.SHADOW_Z` (-1), and `GameMap` draws its floor layers (Border, Floor, BaseArt, Zones, ZoneArt, Decor) one below it**, so the shadows come together in the draw order and batch: a shadow between every pair of sprites cost about half the frame rate at 300 enemies (about 140 down to about 77 fps), and the shared depth brings it to about 115. Walls and trees stay at depth 0, above the shadows.
- **The first map's look.** Grass plaza with flowers, mushrooms and pebbles (12 by 12 sprites; **every sprite stays at the game's one pixel size, never scaled**, a user rule); the mazes, the stronghold and the tunnel all share the one lavender `ruin` floor and the one `stone` wall (user decision after seeing several textures at once), with sparse, evenly spread pebbles and cracks of their own (12 by 12; the first 8 by 8 ones were too small to see); every post is a tree; the plaza's small walls are `hedge`. The brick wall, `path` and `hall` floors and the marble post are drawn but unused.
- **Performance.** Few textures with many uses: stress with `--obstacles --drops` at 300 enemies is the same as main within noise (about 141 against about 135 fps median), so no baking was needed.
- **Art taste (user feedback during the build):** brighter, simpler and more cartoon; fewer textures at once; walls players recognise (stone or brick, not gem-like hedges); trees, not pillars; transitions that look natural.

## Spell and equipment art (Sprint 13c)

- **An element's look is data.** `ElementLook` (`resources/spells/element_looks/{fire,thunder,land,sea}.tres`) holds the hit-area `tint` and `edge`, the `effect_sprite`, the `orb_sprite` prefix and `rises` (Fire and Land rise from the ground, Thunder and Sea fall from the sky). `ElementLooks.for_element(element)` finds it (null for no element, which keeps the flat look) and `ElementLooks.id_of(element)` names an element for sprite variants (`fire`, `thunder`, `land`, `sea`, `none`).
- **Area spells (Cone, Line, Zone).** The exact polygon and hitbox never change. `SpellSkin.dress` tints the polygon and adds a 1 px `Edge` `Line2D`, then spawns effect sprites: `EffectPlan` (pure) gives `count_for(area)` (one per 600 px², 3 to 24), `spots` (best-candidate spread inside the polygon, seeded) and `delays` (rising effects nearest the caster first, falling ones in a random order, over the first 40% of `SpellSkin.INSTANT_LIFE`, 0.35 s; a Zone uses its tick interval). A hybrid spell cycles through its elements sprite by sprite. `SpellSkin.pulse` spawns a fresh set at each Zone damage tick, and `SpellSkin.tint` only tints (the Wave).
- **`EffectSprite`** is a top-level `AnimatedSprite2D` (`play` once, then a fade, then freed) placed in world pixels with its base on the spot, a child of the area's PARENT because an instant area frees in 0.12 s while its sprites play about 0.45 s, and because a rotated or scaled area must not rotate or scale a sprite (one pixel size). At most `MAX_LIVE` (160) live; sets are cached by folder and name (the library's resource cache drops an unheld set, so every spawn built its own frames).
- **Missiles and Waves.** A Missile with an element look shows `Orb` (a `BodyView` on `<orb_sprite>_12|16|24`, class from `MissileArea.orb_class(size)`: up to 1.2 is 12, up to 2.0 is 16, otherwise 24), the node is NOT scaled and only the hitbox is (`_hitbox.scale`), so the hit follows `effective_size()` exactly and no pixel scales; with no art the old square scales with the node as before. The orbs are upright and have no directional trail (they are never rotated). A Wave carries a row of orbs (`WaveArea.orbs()`, one per about 10 px, 2 to 24, top-level, re-spaced every step as it widens).
- **Enemy attacks.** `EnemyProjectile.fire(..., element_id = &"")` (a default, so old calls work): the shot is `fx_enemy_orb` (a ramp sprite, so the element variants colour it) with a dark outline so it stands out from the player's spells; `BrainKeepDistance` passes `enemy.data.element_id`, the boss `ElementLooks.id_of(data.element)`. `BlastZone` warns with rings of `WarningMark` sprites (an outer ring on the circle, a bright inner ring that grows with the fuse and flashes, about one mark per 10 px, at least 8) and ends in `fx_blast_burst` (several for a big zone); without art it draws its old circles. The boss's Charge warning is a dashed line of `WarningMark`s (`Boss.charge_marks()`, top-level because the boss is scaled x3). `TargetReticle` shows `reticle`, with the old ring as the fallback.
- **The wizard is drawn in layers.** `BodyView.add_layer`, `set_layer(layer, sprite, variant)`, `clear_layer`, `layer_names()`: each layer is an `AnimatedSprite2D` above the body that copies its animation, frame and flip every frame (processing is on only while a layer or outline is shown, and layers are counter-scaled like the sprite). `PlayerLook.apply(body, profile, catalog)` sets `robe`, `beard`, `headwear` and `weapon` (the same ownership and slot rules as `ShopSystem.bonuses`); an empty robe or headwear slot shows the starter (`robe_starter`, `hat_starter`), the weapon slot shows nothing and the white beard (`beard_white`) is always worn. `Player._ready` applies it with no profile (the starters) and `RunStart.prepare` applies the profile, so equipping in the shop takes effect at the next run.
- **No skin shows (user request).** The bare wizard (`player_body`) has a face in the hat's shadow with only two eyes, the beard covers the rest, and the hat (a 12 px band and a 14 px brim) and hood are wider than the head; a test fails if any wizard layer or equipment sprite contains a skin colour. `art/sprites/player.sprite` is the composite of the four layers (body, robe, beard, hat) kept as the fallback and as the reference of `test_the_starter_layers_compose_to_exactly_the_wizard`; regenerate the four layers and the composite together.
- **Equipment is data.** `EquipmentData.sprite_name` and `sprite_variant` (a palette variant): `robe_wizard` (fire, land, thunder, sea, none for Ember, Stone, Storm, Tide, Warded), `hat_pointed` and `hood_soft` (hardy, mana, swift), `wand_short` (flicker, quick), `staff_tall` (oak, elder). The equipment sprites are 16x16 with the wizard's eight frames and animations and follow the walk bounce (rows lift one in frames 3 and 5) and the cast; `hat_pointed` is the starter hat's exact shape.
- **Pipeline.** `variants <id> ..` in a `.sprite` limits which colourways a ramp sprite is built in; without it a ramp sprite is built in the five element variants only (`ArtPalette.ELEMENT_VARIANTS`). The item variants reuse colours the palette already has (it sits at 63 of 64).
- **Performance.** Effect sprites cost about 13 to 16% of the frame rate against main in the full stress scene and a Zone (a Line and a Wave are equal), well above the 60 fps target.

## Interface (Sprint 13d)

- **One look, from data.** The HUD and every screen use one committed theme (`resources/ui/game_theme.tres`, `gui/theme/custom` in `project.godot`). `ThemeBuilder` (static, in `scripts/art/`) writes it as text, like `ArtBuilder.set_text`, because `ResourceSaver` gives sub-resources random ids; `tools/art/art_builder.gd` runs it after the sprites and the fonts, and `test_art_assets` fails if the committed file is stale. It reads frame size and slice from the `.sprite` SOURCES and names the sheets `<name>_base.png`, so it can run before the sheets are imported (run `godot --headless --import` before the tool after a new `class_name`, and again after it).
- **Look.** Cream panels with a 2 px plum outline, stepped corners, pink health bar, sky XP bar, **green means go and red means stop** (user feedback after play-testing: it used to be the other way round): green for Confirm, potion Buy and the death screen's Shop button, red for Cancel and Close, yellow for Gold, the selected choice, the equipped item, the active tab and the Interact and Inventory touch buttons, a sky backdrop on full screens. Headings are dark blue (never red). Text is plum on panels and white with a baked dark outline over the world. **One pixel size:** styleboxes tile (`AXIS_STRETCH_MODE_TILE`, a test checks it), icons and glyphs are 1:1.
- **Roles are theme variations, never per-scene overrides.** `Panel`, `PanelContainer`, `Button` (cream), `ButtonRed`, `ButtonGreen`, `ButtonYellow`, `PanelDark`, `PanelSlot`, `PanelSlotSelected`, `HudLabel` (outlined white), `HudGold`, `HudToast` (a dark pill on a Label), `Heading` (red-dark), `Muted`, `Warning`, `BarHp`, `BarXp`, `BarBoss`; `Label` has line spacing 0 because the font carries its own leading. A style whose sprite is missing is left out, so the theme always loads.
- **The font.** `art/fonts/ui.pixelfont` (a text grid: `ascent`, `descent`, then `glyph <code> <advance>` with rows of `#` and `.`; the extension is not `.font` because Godot auto-imports that) is built by `FontBuilder` into `assets/fonts/ui_plain` and `ui_outlined` (BMFont `.fnt` and `.png`). Both builds have identical advances and line height (the outline sits in the 1 px letter gap), so text never reflows. `UiFont.plain()`, `outlined()` and `SIZE` (10, the line height) are the only way code gets a font; the fallback is the engine font. Text must be ASCII 32 to 126 (a test scans for others). Slim: 5 px letters, 7 above the baseline and 2 below.
- **Sliced sprites.** `slice` is valid without `tile`: a panel, button, slot, trough or ring whose corners may be transparent. `SpriteSource.is_surface()` (a tile or any sliced sprite) skips the 1 px margin rule and has no silhouette, and a test checks that a sliced sprite's middle is one colour per row (and per column when it slices vertically) so tiling shows no seam.
- **`UiKit`** builds themed controls: `label`, `button`, `bar`, `icon` and `window(parent)` (the sky backdrop, the cream page and a content area 2 px lower). Screens call it instead of styling by hand; `tests/test_ui_look.gd` fails on a `font_size`, a `StyleBoxFlat`, a fallback font, a non-ASCII text, the word TEMP or a leftover TEMPORARY marker in the UI.
- **Touch sizes (play-test feedback: buttons were too small on a phone).** Main actions (Confirm, Cancel, Close) are `UiKit.ACTION_SIZE` (72 by 28) or bigger, the death screen's Shop button is 96 by 32, the Interact button 64 by 30, the Inventory button 44 by 28, spell slots 34 by 24, potion slots 30 by 22, shop item buttons 22 px tall, merchant potion buttons 32, crafting choices and steppers 24 and crafting slots 28 (`tests/test_ui_look.gd` and the screens' tests pin them). **The crafting screen has two tabs** (`show_tab`: Spell = Base, Area and Range, Buffs = the steppers) because six 24 px rows of each cannot share the screen; the preview, message, Confirm and Cancel stay visible, and it always opens on Spell. The shop shows its message on the top line and its description at the bottom left. The project still scales by whole numbers only, so a phone that fits the game at 1x shows every button at its game-pixel size; fractional scaling would enlarge it but breaks the whole-pixel look (not done, the user's call).
- **The starting-buff screen is colourful.** `BuffEffect.color` and `BuffEffect.icon` (a sprite name, `icon_buff_*`) are data; each option is a tall button tinted pastel by its buff's colour (`self_modulate`, so the text stays plum), with the icon and a pink banner header. A new buff brings its own colour and icon, and a test fails if two buffs share a colour or an icon is missing.
- **The first map has no scattered decoration** (play-test feedback: distracting): every `decoration_count` in `first_map.tres` is 0, the generator and the art stay, and `test_first_map_has_no_scattered_decoration` pins it.
- **Behaviour did not change.** Layouts, input handling (each screen's own touch handling, the bridge, `DeathScreen.handle_event`), pause and focus order are as before. Layout nudges only where the new font or the bigger buttons needed them (the inventory panel is 260 by 214, merchant buttons are two lines). The touch joystick keeps its translucent rings. The death screen has no "Try again" button (restart is R, a controller button or a tap elsewhere).
- Checked in a real window: touch and mouse each buy exactly once in the shop, the focus walk and accept work, and the death screen's Shop tap requests the shop and never restarts.

## Audio (Sprint 13e)

- **Sounds are text, built by the art tool.** `audio/sounds/<id>.sfx` is a recipe (`length`, then `voice <wave> <start_hz> <end_hz> <volume> <attack> <decay>` lines with optional `vibrato <hz> <depth>` and `delay <s>`; waves pulse12, pulse25, pulse50, triangle, saw, noise) and `audio/music/<id>.tune` a pattern (`tempo`, `loop`, then `channel <wave> <volume>` with cells of notes `C4 F#3 Bb5`, `-` rest, `.` hold, `x` a noise hit; `|` is a bar line; a comment is a `#` at the line start or after a space, because `#` is also a sharp). `AudioBuilder` (pure, deterministic: the noise is a fixed shift register) renders them and `WavWriter` writes 22,050 Hz mono 16 bit WAVs (a tune that loops gets a `smpl` chunk, which Godot imports as a forward loop). `tools/art/art_builder.gd` builds them to `assets/audio/` (committed; Godot imports them compressed). `test_audio_assets` fails on a stale or orphan WAV, a silent or clipping one, a loop without its chunk, any source with errors and a total over 3 MB. A line `hand_made` keeps a WAV you made yourself (as `hand_drawn` does for sprites).
- **Data.** `SoundData` (resources/audio): `id`, `volume_db`, `max_voices`, `min_gap_msec`, `priority` (LOW, NORMAL, HIGH), `wobble` (pitch semitones), `pausable` (false for interface sounds), `music`. `SoundCatalog` lists them (`resources/audio/sound_catalog.tres`), `SoundId` holds the ids as constants, `SoundLibrary.find` loads a WAV (null and one warning if missing). Adding a sound is a recipe, a built WAV and a catalog entry; `test_sound_catalog` keeps the three in step.
- **One player, no autoload.** `SoundBoard` (a node in `main.tscn`) owns a pool of 12 `AudioStreamPlayer`s (none made during play), the Music and Sfx buses, the mute state and the music. `play(id)` is silently skipped while muted, before the unlock (a desktop game unlocks and starts the music at once through `Main`'s `start_if_allowed`; on the web and in headless runs `_input` unlocks on the first tap, click, key or gamepad button press, and a restarted board in a browser keeps the page's permission), for an unknown id or missing file (warned once), and for a `pausable` sound while the tree is paused. `VoiceLimiter` (pure) refuses a sound that is too soon after itself or already at `max_voices`, drops LOW and NORMAL sounds when the pool is full, and lets a HIGH one steal the oldest LOW voice (else the oldest), so a boss warning is never lost to a crowd. `requested(id)` fires before any rule (tests and tools listen to it).
- **Gameplay stays unaware.** The board listens to signals that already exist and `Main` calls `bind(self)` last. The new announcements change nothing: `EnemyAttackEvents.bus` (a static emitter: `shot_fired`, `blast_warned`, `blast_detonated`) for enemy shots and blast zones, `CraftingScreen.crafted` and `refused`, `ShopScreen.refused` (and its `last_action`), `MerchantScreen.refused`, `Main.point_effect_applied`. A hit sounds like the element of the LAST CAST (the hit signal carries no element). Every `Button` clicks (`ui_back` for a red one) and ticks on focus through `get_tree().node_added`. A soft step plays every 0.32 s while the wizard walks. `test_audio_guards` fails if any script outside `scripts/audio` (and Main, the sound test and the stress scene) mentions the board, an audio player or the audio server, or if the project gains an autoload.
- **Music.** `music_run` loops from the first input for good (while paused, muted or under the boss loop it keeps its place); `set_boss_music(true)` crossfades `music_boss` in over 1 s from its start and back out (it stops once faded so the next boss starts it again); the Music bus is 9 dB lower while the tree is paused, `duck` lowers it for the level-up and death jingles, and losing focus pauses the music players.
- **Mute.** Input action `mute` (key M, handled by the board, which keeps running while paused; no controller button is free), a `MuteButton` on the HUD (32 by 32, touches and left clicks, hides on death) and `PlayerProfile.muted` (written to the save only when true, so old saves load; applied at start). The board mutes the Master bus.
- **Tools.** `godot --path . res://scenes/world/sound_test.tscn` lists every sound and tune as a button with its numbers (Play all, Stop). The stress scene's `--sound` option wires cast, hit and death sounds to the fight and prints `SOUND started=… dropped=… voices_in_use=…`; no measurable frame-rate cost.
- **Not judged by ear.** The recipes and the two tunes were written from chiptune idioms and checked by tests (length, range, clipping, determinism), never listened to; the user auditions them in the sound-test scene and says what to change.

## Polish (Sprint 13f)

- **What it is.** Two flat things in play were fixed properly (user): knowing how much health is left, and a heavy spell feeling heavier than a spammed one. Everything else is a light touch. It changes how things look, shake and sound, never how they work. Every number is in `ImpactConfig` (`resources/fx/impact_config.tres`: the wait and damage ranges the weight is normalised over, where shake and flash start, the shake size, particle counts, gaps, health thresholds, warning opacity and rate), tuned by feel.
- **Impact weight.** `ImpactWeight.of(spell, config, damage_scale)` (static, pure, 0 to 1) blends the spell's wait (`cast_interval`, 60%) and its damage per hit (40%), each normalised between two config numbers. `AreaEffect._announce_hits` (the one shared base all five Areas build hits through, guarded by an `impact_announced` meta) connects the hitbox's `hit_landed` to `ImpactEvents.bus.hit(position, weight, element_id)`, a static emitter like `EnemyAttackEvents` (not an autoload). `HitboxComponent.try_hit` calls `receive_hit` and then `hit_landed`, so the event arrives after `enemy_damaged`; the hit SOUND therefore comes from the impact event (exact element and weight, a heavy hit plays `hit_<element>` lower and louder through `SoundBoard.play(id, pitch, volume_offset_db)`) and `_on_enemy_damaged` only plays the strong and resisted accents. A ticking area (the Zone) uses its tick interval as its wait, so a Zone tick is a light hit and never shakes or flashes twice a second (review finding). The starting spells weigh about 0.20 (Fire Missile at its 0.6 s cast), 0.32 (Sea Wave) and 0.17 (Land Zone), so none clears the shake threshold (0.35); crafted slow, hard spells weigh more.
- **One effects node, no autoload.** `FxDirector` (a node in `main.tscn`; `Main` calls `bind(self)`) listens to `ImpactEvents`, `EnemyAttackEvents.blast_detonated`, the boss's SLAM, the player's hurt, pickups, level-ups and `ScrollDropper.placed` (a new one-line announcement, emitted at the end of `place`). Gameplay never calls it, and `test_fx_guards` fails if any script outside `scripts/fx/`, `Main`, the sound board, the effects-test scene and the stress scene names the director, burst layer, shake, flash, warning or indicator. A budget keeps a crowd readable: 4 bursts per frame, a pool of 256 particles (the oldest recycled), at most one shake per 80 ms and one flash per 334 ms (never more than three in any second).
- **Parts.** `BurstLayer` + `ParticlePool` (one `_draw`, whole-pixel squares and 3 by 3 twinkles, styles sparks, dust, stars, sparkle, element colours from the `ElementLook`), `CameraShake` + `ShakeTrauma` (sets `Camera2D.offset` to whole pixels, at most 4; `shake(weight)` obeys the threshold, `kick(amount)` is fixed, used by blasts, slams and the player's hurt), `ScreenFlash` (white, at most 12% opaque, 80 ms, only for heavy hits), `LowHealthWarning`, `HitIndicator`.
- **Health awareness.** `LowHealthWarning` (a node in `main.tscn`, bound to the player's `HealthComponent`) has levels 0, 1 (50% and below: the heart on `HealthBar` beats slowly through `HealthBar.beat()` and its second drawing `icon_heart_beat`) and 2 (30% and below: a dithered red frame, `VignetteImage` built in code as a 480 by 270 image because a sliced sprite's middle must be one colour, pulses at 0.8 Hz rising to 2 Hz near death, never above 40% opaque, and `SoundBoard.on_health_beat` plays a quiet `heartbeat`). It clears at once on a heal and on death, and hides behind any paused screen. The wizard also flashes red and jitters 2 px for 0.2 s when hit (`BodyView.set_jitter` moves the whole `BodyView`, shadow included, in whole pixels), throws red sparks, gets a tiny shake kick, and a `HitIndicator` arc (three pooled sprites, `fx_hit_edge_h` and `fx_hit_edge_v`, flipped never rotated) appears at the screen edge on the hit's side.
- **Light touches.** A 4-spark burst where something is collected (a scroll's colour, blue XP, yellow Gold), stars and dust round the wizard on a level-up, a sparkle burst where a Rare scroll lands, and a spell slot whose pool is at or below 25% (and above 0) pulses between its colour and red (`SpellSlotWidget.went_low`, `is_pulsing()`) with a faint `mana_low` blip once when it first drops below (the second new sound, the design said one).
- **Every effect can be switched off.** `FxSettings` (static, all on by default) holds `shake_scale` and `flash_scale` (0 to 1, a value above 1 is never used) and the switches `particles`, `low_health_frame`, `heart_beat`, `hurt_feedback`, `hit_indicators` and `low_mana_pulse` (`SWITCH_KEYS`, `get_switch`, `set_switch`), with `reset()`, `reduce_motion()` (no shake, no flash, no jitter), `to_dict()` and `apply(dict)`. Sprint 15's settings screen only sets these and saves the dictionary (nothing saves or loads them yet). A scale of 0 or a switch off hides that effect only, never the information the player needs elsewhere.
- **Comfort, pinned by tests:** shake at most 4 px in whole pixels, a flash at most 12% opaque and at least 334 ms apart, the frame at most 40% opaque and no pulse above 2 Hz; no effect scene or script scales or rotates (one pixel size); effects freeze with the tree.
- **Tools.** `godot --path . res://scenes/world/fx_test.tscn` (`FxTest`): light, medium and heavy impacts for each element, a health slider (0 to 100%), hit-from buttons, pickup, level-up, rare and blast buttons, the shake and flash scales, one toggle per switch and a readout of weight, trauma, particles and warning level; it restores `FxSettings` when closed. The stress scene's `--fx` option adds the director and prints `FX particles_max=... shakes=... flashes=...`.
- **Measured** (`--enemies=300 --seconds=8 --obstacles --drops`, three runs each): about 108, 107 and 121 fps without effects and 96, 107 and 107 with `--fx` (106 with `--boss --fx`), inside the usual noise; the pool peaked at 95 and shakes stayed within their gap. Checked in a real window: 45%, 25% and 8% health (the heart, the frame, rates 0.5, 1.0 and 1.68 Hz), a heal and a death clear the warning at once, and the crafting screen at low health shows no pulse behind it. **The feel was not judged** (I cannot feel it): the numbers are starting values for the user to tune in the effects-test scene.

## World pass (Sprint 14a)

- **Why:** play-testing found the points of interest close together and the Lecterns exposed in the open, and the bottom-left bare. The rule (user): spread them evenly, and every point of interest and Lectern has something to get through, like the maze centres, the corridor and the island. Map data only (`first_map.tres` plus tests), no code or art.
- **Guards.** A **ring** is seven `tree` circles (radius 18) at radius 62 round a centre, at angles `gap + 60 + 40k`, leaving an opening of about 70 px facing `gap` (the clearing is about 88 px across). **Neighbouring trees must leave a slit under 12 px** (they leave about 6), because the player is a 12 px box and the first version, six trees of radius 17 with 13 px slits, let the player walk through the side (found in the review; `test_no_gap_between_ring_trees_lets_the_player_through` pins it). The chest and the north and west Lecterns have one. The merchant has a five-piece `hedge` yard (160 by 136, gate west), and the east Lectern a hedge room (walls at x 1640 with a gate at y 404 to 484, x 1852, and a cap at y 340 from x 1748 to 1860, so the gate is its only way in, merging into the island and maze walls). The bottom-left also has two clumps of three overlapping trees, like the old groves.
- **Layout rules that shaped it (tested in `test_first_map_world_pass.gd` and the older layout tests):** every point of interest at least 400 px from the next, Lecterns at least 700 px apart and 400 px from the start, each guard has exactly one opening (the free rays of 16 at 170 px, grown by the player's 6 px half-width, form one run of at most 5) and its opening leads to open ground. Circular clearings centred off the 16 px grid leave one-cell edge rows that the narrow-gap test rejects, so ring centres sit on cell corners (multiples of 16), and a ring needs 48 px or more of lane to the nearest wall (the west ring sits at y 688, because at 656 its top left a one-cell lane under the north-west maze). A ring that leaves a lane under 48 px to a wall leaves a sliver, so every lane is 48 px or more or merged into the wall (the 184 px strip east of the island is too narrow for a ring, hence the room). Four old hedge walls were removed because they crossed new guards: (200, 740), (280, 740), (990, 180) and (990, 260).
- **Not judged:** whether the layout feels better is the user's call; positions were checked by tests and screenshots.

## Balance (Sprint 14b)

- **The Missile bursts (data, not a special case).** `AreaData.burst_radius` and `burst_damage_share` (both 0 for every Area but the Missile: 18 px and 0.5). `MissileArea._end` runs once (its hit limit or its range, never an obstacle, because player spells pass over obstacles) and spawns one `MissileBurst` (an `AreaEffect` with a circular hitbox, built through `_configure_hitbox`, so the element, damage scale, attack profile and impact announcement are the spell's own) that hits every enemy in the radius, the one it hit included, once for `damage * share` (`_configure_hitbox(..., strength)` scales the damage, the knockback AND the weight it announces by the share, so a burst never pushes or shakes like a full hit; review finding). Duplicate Area bursts per copy. `MissileArea.burst_spawned` is for tests. The first radius, 36 px, was "massive" and almost stole the Zone's role (user feedback), so it is 18 px; the Missile casts every 0.6 s (was 0.35), in both `area_stats/missile.tres` and `fire_missile.tres` (a test pins that a crafted Fire plus Missile equals the starting spell but for the pool).
- **The Cone** (user feedback after play: Short was impractical against fast enemies, and it was the strongest spell): Normal range 56 to 94 px (Short about 56, what Normal was), baseline cast interval 0.55 s to 0.8 s (the starting Sea Cone 0.4675 to 0.68). Starting values for the user to tune.
- **The audit.** `SpellAudit` (`scripts/systems/`, pure) and `godot --headless -s scripts/dev/spell_audit.gd` print damage per full pool, per second and casts for every Base and Area pair, every buff on Fire Missile and the starting spells, against a tight group of 1 and of 8, and flag rows beyond 3x the median. It is a MODEL with stated constants (the group radius, Line 3, Cone 6, Wave 5 targets, a Zone hitting every tick), not play data, and it changes no number. First run: the four Zones sit at 5x to 6x the median damage per pool and 5x to 10x the damage per second of the other Areas against 8 enemies; the crafted Missile with its burst is near the median. Whether to change the Zones is the user's call.

## Performance, soak and tests (Sprint 14c)

- **The overlay.** `PerfOverlay` (a node in `main.tscn`, `scenes/ui/perf_overlay.tscn`) shows `fps 98  10.2 ms  enemies 300  nodes 1423` at the top centre, refreshed 4 times a second, and does no work while hidden (`set_process(false)`). `FxSettings.perf_overlay` (default **false**, the one switch that starts off, in `SWITCH_KEYS`) is the single source of truth; `Main.toggle_perf_overlay()` flips it and calls `PerfOverlay.sync()` (FxSettings is static, so nothing notifies). F3 (`debug_perf_overlay`) and a 1 s long press on the HUD's mute button both call it. It never takes a touch.
- **The mute button now acts on release.** `MuteButton` starts a hold on a press inside it (`hold_started`, which makes `Main` block casting at once, because the click is still down; it tracks the finger index, so another finger's release is ignored), emits `pressed` when the press is released inside before `HOLD_SECONDS` (1.0), emits `long_pressed` once at 1 s (the hold then ends, so the release does nothing), and a release anywhere else cancels. Processing runs only while a press is held. Checked in a real window for touch and left mouse.
- **The soak test.** `SoakRun` (pure: `take`, `trend_slope`, `verdict`) and `SoakDriver` (`scripts/dev/`) plus `godot --headless --fixed-fps 60 -s scripts/dev/soak_test.gd -- --rounds=12 --frames=600`. Each round keeps a crowd, casts every Area, kills enemies, walks onto pickups, adds XP, buys and drinks a potion, fights a boss on round 2, then settles (kills everything, lets deaths and effects finish, frees what dropped), samples, kills the player and restarts with a fresh `Main`. **Sampling at rest and restarting every round are deliberate:** sampling during play, or restarting every third round, gave swings from the crowd and from pickups piling toward their caps (100 scrolls, 150 gems, 150 coins) that look like leaks but are load. The verdict needs every count within a band of its first post-warm-up value, no orphan growth and no steady climb over the second half (`SLOPE_LIMIT` 0.5% of the base per round). First real run: nodes exactly 620 each round, orphans 0, static memory 46.3 to 47.5 MB then flat, so **nothing that survives a restart leaks** (a leak that only lives inside one `Main`, such as a pool that grows during play, is erased by the restart and the pickup/projectile freeing, so it is NOT covered: use `--restart-every=N` with a wide band to look for one). `tests/test_soak.gd` runs 8 rounds of 90 frames (band 0.5) and a deliberate leak of 5 nodes a frame must fail it.
- **Test coverage.** The Sprint 14 test list was mapped to existing tests (the table is in `development-log.md`); `tests/test_combinations.gd` fills the gaps (every Base and Area pair casts and spends exactly its cost, every buff at its stack limit and all together, five slots with separate mana, every robe, weapon and headwear combination adds up, a save round-trips every field, a restarted run is clean). None found a bug.
- **Measuring needs a steady machine.** The stress scene is only comparable when the laptop is plugged in and not in Low Power Mode: on battery with Low Power Mode the same 300-enemy scene swung between about 100 fps and 10 to 45 fps between runs. No optimization was made for that reason. A phone has not been measured; testers open the overlay and send a screenshot.
- **Fixed minors:** the burst is spawned by a static function holding weak references (`MissileArea._spawn_burst`), `SpellAudit.rows` skips a missing scroll and finds Normal by label, the point-of-interest prompt label is 120 px, and an old save's potions show "Your old potions were sold for N Gold."

## Front door (Sprint 15a)

- **The game opens on a home screen.** `project.godot` `run/main_scene` is `scenes/home/home.tscn` (`HomeScreen`): Play (opens the map select since 16a), Shop, Tutorial (live since 15b), Settings, New game and a Full screen button. It loads the progress save and the settings itself and holds the `ShopScreen`, `SettingsScreen` and `ConfirmDialog` as child scenes (Main-style; creating them with `load()` leaked at exit). **The run scene is not created until a map is chosen**: `HomeScreen.play_map(entry)` only calls `SceneSwitcher.change_to` with the catalog entry's scene path (see Maps below), and a guard test fails if the home script names `main.tscn`. A run launched directly (the stress scene, tests, the editor) still works; `Main._ready` applies the saved settings only when `save_path` is the real default, so no test or tool ever reads the player's real settings.
- **Settings are their own file** (`user://settings.json`, `SettingsStore`, versioned JSON written through a temporary file and a rename; a missing file is defaults, an unusable one is kept as `.bak`, unknown and mistyped values are ignored). It holds `GameSettings` (`music_volume`, `sfx_volume` 0 to 1 default 0.8, `fullscreen`) and `FxSettings.to_dict()` (every effect switch and strength, including the performance overlay). New game erases progress and **keeps settings**. A change applies at once (`SettingsEvents.announce()`, a static emitter like `EnemyAttackEvents`: `SoundBoard.apply_settings` sets the Music and Sfx bus volumes, 0 is -80 dB, and `PerfOverlay` re-syncs) and is saved at once. `ScreenMode` (static, with a getter and setter seam for tests) toggles full screen; a browser allows it only inside a tap, so a saved full screen is applied at start on a desktop and never on the web.
- **Screens.** `SettingsScreen` (music and effects sliders, shake and flash strength sliders, a toggle per effect switch, a Full screen toggle, Reduce motion, and Controls and Credits pages; `ControlsText.lines()` reads the real keys from the Input Map, `CreditsText.LINES` is where the credits are edited) and `ConfirmDialog` (Cancel red and focused first, confirm green, Esc, back and a tap outside cancel, confirming is ignored for 300 ms after it opens so a held button cannot confirm). Both, and every new screen, run while the tree is paused and handle their own touches (`TouchBridge`; the settings screen also bridges drags so a slider can be dragged). **Esc is taken in `_input` by the dialog and Settings (marking it handled) while the pause menu uses `_unhandled_input`, so one key never does both.** Anything that closes by a bridged tap and changes scene (Play, Quit) must take `get_viewport()` before handling, because the scene change removes the node (found in a real window as a null-viewport error).
- **New game** asks twice (the first question names what is erased, the second says it cannot be undone and has its own input guard) and the second Yes calls `SaveGame.erase`, which moves the save aside as `save.json.bak` (replacing an older backup; the project never deletes a save) and reloads a fresh profile.
- **Pause.** `PauseMenu` (a node in `main.tscn`, process mode Always): Resume, Settings, Quit to home (asks first; unpauses before the scene change). It opens on `pause` (Esc, controller Start) when `available` allows it (`Main._pause_menu_available`: alive and no crafting, shop, merchant, pick screen or inventory open) and from the HUD `PauseButton` (a plain "II" button left of the mute button), all through `GamePause.set_paused`, so `GameTime` and the run clock stand still. `InventoryPanel` and `InventoryButton` are process Always and the panel pauses on open and unpauses on close (a redundant close never unpauses something else's pause); they close on `toggle_inventory`, `pause` and Esc because Main's own handlers do not run while paused. The death screen has a Home button beside Shop (handled like the Shop tap: it goes home and never restarts).
- **Checked in a real window** (touch and left mouse by `Input.parse_input_event` in window coordinates): the home screen's buttons, Settings (a toggle flipped, a slider set by tapping 25% of its width, the saved file changing), both New game questions (the save became `.bak`, settings kept), Play, Esc and the HUD button opening the pause menu with the run clock frozen and resumed, Settings inside the pause menu, the inventory pausing and closing from its key and from its button, and the death screen's Home. **Not checked on a real phone.**
- **Review fixes:** leaving a run (Quit to home, the death screen's Home) calls `ProfileSaver.save_now`, because the saver only writes every 10 s and the dialog says XP and Gold are saved; `ConfirmDialog` and the death screen set `focus_neighbor_*`/`focus_next` explicitly (buttons that are direct children of a CanvasLayer have no neighbours, so a controller could not confirm or reach Home); and `Main._toggle_inventory` opens the panel only when nothing else is open (the button works while paused, so it could otherwise open the inventory behind the merchant or pick screen and later unpause them).
- **Known quirk:** a headless run that exits from the home scene logs "ObjectDB instances were leaked at exit"; the run scene exits clean. A shutdown-order message, not a runtime leak; not investigated.

## Onboarding and run statistics (Sprint 15b)

- **The tally.** `RunStats` (`scripts/progression/`) only LISTENS to announcements the game already makes (the spawner's `enemy_died`, `RunDirector.boss_defeated`, the pickup collector, `CraftingScreen.crafted`, `PotionBelt.used`, `RunProgress.leveled_up`) and never calls into gameplay (a guard test scans it). `Main` makes a fresh one per run and freezes it first thing in `_on_player_died`. An enemy counts as defeated only when it `gives_rewards` (an Exploder that blasted itself is not a defeat) and a boss counts only as a boss. At death `Main` copies XP, Gold and level from `RunProgress` (`run_xp`, `run_gold`, `level()`) into the tally, because those also count XP that did not come from a gem and the level is the level REACHED (a level-5 player who dies without levelling shows 5).
- **The bests (per map since 16a).** `PlayerProfile.bests` maps a map id to `{"seconds", "enemies"}` (helpers `best_seconds(map_id)`, `best_enemies(map_id)`, `set_best`), saved as one optional `bests` object in the progress save (version stays 1, written only when any is above 0, whole numbers checked like any field, a bad value is a bad save; the old flat `{"seconds", "enemies", "level"}` loads as the ruins' (`first_map`) bests and its level is dropped). `RunRecords.update(profile, map_id, enemies, seconds)` records any best the run beat and flags a stat only when the OLD best was above 0 and the run beat it: the first run sets its bests without "New best!", a tie or a worse run changes nothing. `SaveGame.erase` (New game) takes the bests with the save.
- **The death card.** `RunRecap.rows(stats, seconds, profile, flags, saved, map_id)` builds eight rows (time survived, enemies, bosses, XP, Gold, scrolls, spells crafted, potions drunk; the level row went in 16a because the permanent level always shows the same number); only time and enemies have a best, the best on that map ("best 7:10"); "New best!" replaces the best and is shown only when `ProfileSaver.save_now()` succeeded. `DeathScreen.set_recap(rows)` and `recap_text()` replaced the one-line `set_run_summary`; the card is 400 by 186 with a single column of rows, a hint line, and the Shop and Home buttons below. Order at death: freeze, copy, `RunRecords.update`, save, set the recap.
- **The Tutorial.** `TutorialPages.pages()` (four `TutorialPage`s: Survive, Cast spells, Scrolls and the Lectern, Potions and the shop; edit the wording there) and `TutorialScreen` (a node in `home.tscn`; Back, Next, which is Done on the last page, Close, a page counter, left and right turn the page, Esc or back closes; process Always; bridged touches; explicit focus neighbours between its buttons). Key names come from `ControlsText.key_for` and `keys_for` (the Input Map), and two rules the player most needs are pinned by a test: "Mana never comes back" and potions last "one run". Pictures are `BodyView`s drawing each sprite's first animation at 1:1, so they are small. It opens only from the home screen's Tutorial button (no pop-up), and closing returns focus to Play.
- **Review fixes:** one push of the controller's left stick sends many motion events that each count as a "pressed" `ui_right`, so the Tutorial skipped pages and closed on the last; it now pages once per push (`_stick_turn`, back to neutral to page again). The potions page builds its numbers from the game data (the merchant's `stock_per_potion` and `RunPotions.MAX_POTIONS`), so it cannot drift.
- **Scene-change audio bug (found by the user, fixed):** quitting a run to the home screen logged "Playback can only happen when a node is inside the scene tree". `SoundBoard` wires every new `Button` through `get_tree().node_added`; during a scene change the old board is out of the tree for a frame while the next scene's buttons arrive, so it wired them, and the home screen's first focus made it play from outside the tree. Now `play` returns when the board is not in the tree and `_exit_tree` disconnects `node_added`.
- **Checked in a real window** (touch and left mouse): the Tutorial opened by touch and by mouse, three Next taps, Back, Done, Close, Play focused again; the death card with a new best and saved bests. A very first run in a fresh process missed its first tap (the layout was not settled after a fresh import); repeats were clean. Not checked on a phone.

## Maps and the map select (Sprint 16a)

- **Three maps, one catalog.** `MapCatalog` (`resources/maps/map_catalog.tres`) lists `MapEntry`s (a `MapData` and a run scene path) in order: the forest (`forest_map.tres`, `scenes/main/main_forest.tscn`), the ruins (today's `first_map.tres`, id `first_map`, `main.tscn`, display name "The Ruins") and the maze (`maze_map.tres`, `main_maze.tscn`). The forest and maze scenes are tiny inherited scenes of `main.tscn` that override only the `GameMap`'s `map_data`; the chosen map lives in the scene path (no static "current map"), so a death restart reloads the same scene. `MapCatalog.find(id)`, `entry_for_scene(path)`, `ids()`, `default_id()` (the forest) and `MapEntry.boss_name()`. `Scenes` has `FOREST` and `MAZE` beside `RUN`. Nothing branches on a map id.
- **Everything but the layout and the art is the same on every map** (user decision): types, elements, stats, the shared default spawn config, rewards, bosses on the 300 s timer (no lair), all 1920 by 1080, all open from the start. Difficulty is the layout. `MapData` gained `description` (the card's theme line) and `enemy_art_set`.
- **Art sets.** `Main._apply_map` hands `MapData.enemy_art_set` to `EnemySpawner.enemy_art_set`, which sets `Enemy.art_set` before `setup` (`_spawn_enemy` is the only place enemies are made). `Enemy.look_sprite()` is `enemy_<set>_<type>` when the set is named and that sprite exists, else `enemy_<type>`; no sprite was renamed, so in 16a every map shows today's art and 16b to 16d add sprites that override it. Bosses are unchanged (`boss_<id>`).
- **The forest** (`forest_map.tres`, generated once by a scratch script, then pinned by `test_forest_map_layout`): open grass, only `tree` circles (no rock art exists): five seven-tree rings (the 14a recipe) around the three Lecterns, the chest and the merchant, each with one opening toward the middle, twelve three-tree groves, the shrines and Rare spots in clearings (nothing within 80 px). 71 shapes. Shared checks are in `tests/map_layout_checks.gd` (preloaded, no `class_name`).
- **The maze** (`maze_map.tres`, seed 10, `test_maze_map_layout`): one `MapMaze` (`Rect2(80, 60, 1760, 960)`, 22 by 12 cells, `clear_center`, 10 extra openings, **two entrances** (north and south) because a closed maze seals the band round it and an enemy spawning there would be stuck for ever), floor `ruin` at map level (no zone), stone walls, 139 shapes. Every Lectern and point of interest stands in a dead end (`MapMaze.dead_end_cells()`), the start in the cleared 160 px centre room (so the 150 px start-area rule does not apply to this map).
- **The map select** (`MapSelectScreen`, a `CanvasLayer` in `home.tscn`, process Always): Play opens it; one card per catalog entry (a `MapPreview` schematic drawn from the map's own data at 1/15 scale, the name, the wrapped theme line, "Boss: ...", "Best: m:ss" or "No best yet" on that map), Back and Play. **Touches are decided by where they land** (`handle_event`: a card starts its map, Play starts the focused one, Back or anywhere else closes), not bridged; the viewport is taken first because choosing changes scene; a 300 ms guard (`input_guard_msec`) ignores the press that opened it. Focus starts on the last played map. `HomeScreen.play_map(entry)` remembers the map (`GameSettings.last_map`, saved in `settings.json` under an optional `play` object; an id not in the catalog means the first card) and loads the scene through `HomeScreen.scene_changer` (a Callable; empty uses `SceneSwitcher`; **tests must set it**, because a test that really changes scene breaks every later test in the run: found as 16 deterministic failures in the full suite while each file passed alone).
- **Performance finding.** In the stress scene the maze ran about 40% below the ruins (7.6 against 11 to 14 fps on a throttled laptop): every enemy near the player tested every wall shape in `ObstacleMap.line_clear`. `ObstacleMap` now keeps each shape's box and skips shapes whose box cannot touch the segment grown by the body radius (answers are exactly the same, pinned by an equivalence test on all three maps); afterwards the maze was at or above the ruins in interleaved runs. The stress scene takes `--map=<id>` (implies `--obstacles`; `StressTest.map_for_id` reports an unknown id).
- **Order check** (a throwaway kiting bot, 300 simulated seconds, two seeds; reported, not asserted): survival forest 75 and 48 s, ruins 58 and 42 s, maze 43 and 38 s, so forest easiest and maze hardest, as intended (small sample).
- **Checked in a real window** (throwaway `HOME`): Play opens the select by touch and mouse, a touch on the forest card and a mouse click on the maze card load their scenes, the last map is remembered, a tap outside closes; whole-map views and a close-up of every placement on both new maps. A screenshot found theme lines not wrapping (a label's size set before its autowrap is stretched to the text width): fixed with a failing test first.

## Web build and GitHub Pages

- `.github/workflows/deploy-web.yml` builds the `Web` export preset with Godot 4.7.2 and publishes it with GitHub Pages. It runs when `main` changes and from the Actions tab ("Run workflow"). It downloads the Godot editor and the export templates for the version pinned in the workflow's `GODOT_RELEASE`, checks them against Godot's published SHA-512 sums, and caches the editor and the two web templates it needs. **When the project moves to a new Godot version, change `GODOT_VERSION` and `GODOT_RELEASE` there.**
- One-time setup (a repository setting, not code): Settings > Pages > Build and deployment > Source: **GitHub Actions**. The game is then at `https://jtexpo.github.io/GODOT-SpellCraft-Survivors/` (the last part changes if the repository is renamed).
- The preset is single-threaded (`variant/thread_support=false`, no extensions), because GitHub Pages cannot send the cross-origin isolation headers a threaded web build needs. PWA mode is off on purpose, so a phone never serves a stale cached build while testing. `exclude_filter` keeps GUT, the tests, the docs, `.github`, `venv` and `export` out of the package.
- Web builds need the `gl_compatibility` renderer, which the project already uses. The exported package is small (about 225 KB) and the engine file (`index.wasm`) is about 39 MB uncompressed.
- The `export/` folder is gitignored. To check an export on a machine **without installing templates into Godot's own folder**, make a throwaway copy of the project (for example with `rsync`, leaving out `.git`, `venv`, `.godot` and `export`), unpack only `templates/web_nothreads_release.zip` and `web_nothreads_debug.zip` from the `.tpz` into a scratch folder, and in the copy's `export_presets.cfg` set `custom_template/release` and `custom_template/debug` to those zip paths. Then run `godot --headless --path <copy> --import` and `godot --headless --path <copy> --export-release "Web" <copy>/export/web/index.html`, and serve that folder with `python -m http.server` on 127.0.0.1. Delete the copy afterwards.
- The F9, F10 and F12 debug keys are keyboard-only, so a phone has no way to give itself scrolls or XP. Touch testing means playing for drops.

## Touch and input gotchas

- A `ColorRect` (like any `Control`) stops mouse and touch input by default (`mouse_filter` STOP), and a visible one swallows the event before `_unhandled_input` sees it. World decorations (the arena floor, the player and enemy bodies, Lectern parts, projectile bodies) must set `mouse_filter = 2` (IGNORE). `tests/test_world_input.gd` fails if a world scene gets a Control that stops touches. A phone's "tap to restart" was broken for exactly this reason: the arena floor covered the whole screen.
- Anything that must react to a tap anywhere (the death screen) listens in `_input`, which runs before any control, not in `_unhandled_input`. Widgets that handle their own touches (`SpellSlotWidget`, the Inventory and Interact buttons, `TouchJoystick`) already do.
- In headless GUT runs pointer events (mouse and touch) reach `_input` but never `_unhandled_input`, while keys reach both. So a headless test cannot show a swallowed tap. Check touch behaviour with a throwaway real-window script that sends `Input.parse_input_event` touches in window coordinates (multiply the game position by `root.get_final_transform()`), as was done for the touch bridge and for this bug.
